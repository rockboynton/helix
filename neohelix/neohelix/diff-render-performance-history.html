Historical diff renderer experiments

These are development-time measurements, preserved for provenance. For the current implementation, acceptance target and results, see diff renderer performance.

Historical serial worker across unseen revisions: 2026-10-16

The following measurements describe the earlier serial implementation, before the parallel retained-renderer changes above.

Each sequence visits every revision once, with a new worker per trial/layout, three trials and alternating mode order. The existing worker is not a performance win for this unseen-revision suite. It retains the loader/configuration and a bounded exact-content document cache, but performs serial file rendering; the one-shot path uses up to four threads. Document reuse additionally requires matching displayed coverage and theme. There is no cross-revision, changed-source incremental tree lookup: incremental updates currently copy only the same request’s before tree into its after tree. Matching source bytes alone do not prove a tree/style-cache hit.

These results do not rule out a persistent parallel renderer with broader AST reuse, but they do not justify enabling the existing worker by default. Its serial architecture must not be presented as that future implementation.

Invocation-local parallelism and incremental parsing: 2026-10-16

Complete-source first views now use bounded parallel directory rendering and before-to-after incremental syntax reuse. The baseline tree remains unchanged; an unavailable baseline tree or failed incremental update falls back to fresh complete parsing. Background output is ordered and spills past 1 MiB to private temporary storage; at most three background file renders run at once. Inputs above 512 KiB per side stay on the main thread to avoid concurrent large forests. The first file still streams directly. There is no persistent process.

Delta source audit: 2026-10-16

Inspected Delta 0.20.1, commit b88d2290468449d75950bfa150ea7c1291fe2977, the version used in the comparisons. Its relevant design choices are:

  • It consumes the patch stream, not complete source syntax trees. Each hunk resets the Syntect highlighter; omitted source is not parsed for context. See hunk headers and line highlighting.
  • Nearby changed lines are buffered for word alignment, with a default buffer limit of 32, rather than waiting for an unlimited changed block. See hunk processing.
  • Highlighting is capped at 400 characters per line by default. Remaining text is rendered without syntax styles; the source explicitly notes possible subsequent highlighting errors until the next hunk reset. See defaults and the highlighting branch.
  • Syntax/theme assets load from Bat’s asset cache or its embedded bundle, and styled output accumulates in strings before being emitted. See assets and painting.
  • Comparing paths invokes git diff --no-index (or diff for some process substitutions), then processes that resulting patch; it does not build full source ASTs. See path comparison.

Directly reusable without changing syntax semantics: bounded buffering, reused output storage, and prebuilt/validated resource caches. Neohelix’s flow emitter now appends sanitized cell text into reusable row storage and writes once per row, avoiding an allocated string and tiny write for every cell. Output remains byte-identical, including SGR, wide/combining characters and control sanitization.

Not silently adopted: replacing complete-source Tree-sitter context with isolated hunks, truncating syntax highlighting, or changing word matching merely to meet a timing target. Neohelix’s explicit raw-patch input already has a fragment-based contract; the benchmark supports --patch to compare that separately with Delta using identical patch bytes, without claiming complete-source syntax accuracy.

Reproduce first views of complete-source revisions with shared resources primed but source-style caches cleared before every measured invocation:

  --hx target/rust-1.99/release/hx --iterations 3

The harness interleaves 1/2/4-thread fresh processes and checks every result against serial, cache-disabled, non-incremental full parsing. Add --patch --threads 1 for the distinct patch-stream comparison. No worker runs and the OS filesystem cache is not flushed. Exact duplicate sources inside a single invocation may reuse work; no source styles survive from earlier trials.

Session experiments

The session experiments below preceded the Unix worker transport. File-based hx --render-diff now automatically uses that transport; see the worker guide. Historical session timings below exclude IPC and are not end-to-end worker measurements. Set HELIX_DIFF_WORKER=0 when reproducing a fresh-process baseline.

diff_render::RenderSession retains the evaluated configuration, theme/icon resources and language loader across sequential requests in one workspace. Each request still reads the input files. A content-addressed LRU now retains read-only parsed documents (64 entries, 16 MiB of source bytes; document/tree allocations add memory beyond that budget). Lookup verifies exact bytes and detected language, not just a hash or file metadata. This survives jj’s temporary snapshot paths without reusing a tree for changed contents or the wrong language. Failed syntax parses and entries larger than the byte budget are not retained. The session does not cache rendered output or diff results. The worker owns its session and recreates the process when configuration, runtime or trust changes.

Build the production CLI and benchmark with the same release profile:

cargo build --locked --release -p helix-term --bin hx --example diff-render-bench
HELIX_RUNTIME="$PWD/runtime" target/release/examples/diff-render-bench \
  /absolute/path/before /absolute/path/after inline 20

Use the same working directory and environment as the CLI comparison so user and trusted-project configuration are identical. The example evaluates Steel once, measures initialization and the first render separately, then reports the median/minimum/maximum of subsequent renders. All repeated outputs must match byte-for-byte. Both files and directory pairs are accepted, in inline or side-by-side layout. DIFF_BENCH_OUTPUT=/tmp/session-output optionally saves the first output for comparison with the normal CLI.

Compare against multiple fresh CLI invocations using the same width (160), layout, paths, and --color always. Measure elapsed wall time through process exit; redirect/capture output identically for every run. Report warm filesystem cache results as such, not as cold starts. Repeated identical inputs isolate retained resources, including parsed documents; they do not by themselves demonstrate how the cache behaves when navigating different revisions.

Set DIFF_BENCH_PROFILE=1 to report average per-file read, document preparation, syntax, diff and rendering times over the warmed requests. These times cover changed non-binary text pairs with hunks; totals exclude traversal/setup/cleanup and other overhead. The document total includes both prepare and syntax.

For navigation, set DIFF_BENCH_SEQUENCE to a JSON manifest of [["left-directory", "right-directory", "expected-CLI-output-file"], ...]. The example then executes each request once, starting with an empty cache, and checks every output against independently captured CLI output. No requests are warmed before this sequence. Supply the desired layout through the normal positional argument. Include reversed requests to measure revisiting revisions. The example also accepts DIFF_BENCH_CACHE_ENTRIES and DIFF_BENCH_CACHE_BYTES to compare limits without rebuilding. Zero entries disables parsed-document caching. Navigation reports entry/source-byte usage, not total process memory.

The worker now handles session invalidation, workspace isolation, serialized requests, lifecycle and transport failure separately from this benchmark. These session measurements exclude jj’s snapshot/export work, IPC, and terminal rendering.
