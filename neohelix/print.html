Neohelix

This book documents Neohelix: Helix’s editing model plus this fork’s native diff/review tools, Steel configuration and plugins, Jujutsu support, file watching, folding, media previews and shared language servers.

Start with the acceptance walkthrough to try features and check expected behavior, or the review cheat sheet for quick commands. See the guides in this section. Neohelix acceptance walkthrough

Mark each checkbox pass / fail / skipped, and record failures as build + OS + terminal/Zellij version + action + expected/actual. Record hx --version and your config revision first. This is a manual acceptance plan, not a claim that every platform has passed it.

Setup: disposable data, real config

Run this in Bash (bash first if your login shell is Fish), from the Neohelix checkout, using the binary you want to test:

HX=hx                         # or an absolute checkout release-binary path
TESTROOT=$(python3 contrib/neohelix-test-fixture.py --large-mib 16)
printf '%s\n' "$TESTROOT"      # keep this path for every terminal used below
"$HX" --version
cd "$TESTROOT/git"
"$HX" src/lib.rs

Use --without-jj on the fixture helper if JJ is unavailable. It creates only temporary local repos, directory snapshots, Git/JJ patches, three-way variants, a CSV and a PNG. No real repo, remote, user config or bookmark is modified. Commands below run from $TESTROOT/git unless another directory is specified. Keep all editing/history experiments inside these fixtures. Use a fresh fixture when an earlier test changed inputs. No failure should cost real work.

Keys assume the optional user keymap; commands work without it. Test once in direct Ghostty/Kitty, then repeat relevant checks in Zellij. Use Zellij locked mode when Alt keys are intercepted. A checkout binary needs its matching runtime; installed/Nix binaries already supply that runtime.

For unsaved-edit tests, disable autosave in every editor: :set auto-save.focus-lost false, then :set auto-save.after-delay.enable false. Repeat after config reloads. Do not mistake autosave + filesystem reload for live shared-buffer synchronization.

1. Startup, configuration and ordinary editing

  • Semantic colors: in Rust, wait for rust-analyzer, then run :toggle lsp.semantic-tokens. Types, fields and resolved symbols use your theme; syntax colors remain immediate with the option off or the server busy. Edit and restart the server; old token positions must not color unrelated text.

  • Commit gutters: edit and save a fixture file, leave another buffer dirty, then jj commit -m test externally. Saved changes lose their gutter markers automatically; unsaved text and cursor positions remain untouched.

  • Steel/trust: decline any initial trust prompt. Before trusting, :get text-width shows your user value. Run :workspace-trust; it becomes 88 from the fixture’s project Steel layer. :workspace-untrust restores the user layer; trust again for later tests. Neither command demands a TOML file. :config-open opens your active config.

  • Reload/display: :config-reload retains your theme, icons and bindings. Check relative numbers, cursor shapes, indent guides, search-position count, and transparent background in Zellij. Re-disable autosave afterward.

  • Selections: select a subword in my_http_value, try your subword motions, use the command picker to switch case (snake/camel/Pascal) in the README, and try closest-pair selection on ((nested)). Only the intended text/range changes; undo restores it.

  • Trim/history: select the trailing-whitespace comment and run :trim; only selected trailing spaces disappear. Run several commands, open command history (Space :), then yank different selections and open register history (Space H in your config). Entries can be selected/reused.

  • Language overrides: open Rust, Scheme and data.csv. Normal syntax, CSV quoted-field highlights and your configured language servers/formatters apply. On a Rust symbol, your Space K opens hover docs in a buffer.

2. Pickers, tree and safe external reload

  • Previews: rapidly move through file-picker entries, including Rust, Markdown and CSV; scroll the preview. Syntax colors remain theme-correct; no plaintext-then-highlight flash or stale previous-file result. A temporary loading placeholder is allowed, not a zero-latency guarantee.
  • Diagnostics: introduce an unsaved Rust type error; open diagnostics and narrow the list. The selected message wraps inside its column. Alt-]/Alt-[ scroll a tall message without covering the preview; selection resets scrolling. Undo the error.
  • Tree: Space e toggles visibility; Ctrl-w e toggles focus both ways; Space E still opens the current-buffer-directory explorer. Test icons, expand/ collapse, /lib filtering, n/p, Enter, Escape, H/L, and ?. Selection and expansion survive hiding/showing; clearing a filter restores browsing state.
  • Watcher: in another terminal, edit or atomically replace a clean fixture file. Helix updates promptly and undo can restore prior text. Repeat with an unsaved edit in Helix: local text must survive. Test external deletion too. Use normal mode and autosave off; do not wait 30 seconds as the expected latency.
  • Refactoring: :global-refactor NEOHELIX_SAMPLE; edit the matching text, keeping result lines intact; :refactor-apply updates source buffers without saving. Undo there. Repeat after externally changing an affected source: stale results must be rejected, not silently applied.

3. Editable diffs, complete reviews and folds

  • Two-file split: :ds ../before/src/lib.rs src/lib.rs. Expect two columns, your normal syntax/gutter colors, muted line fills, stronger changed-word fills, aligned blank rows and synchronized scrolling. Repeat :ds: no third pane. Compare ../before/bindings.kdl with bindings.kdl: swapped actions emphasize changed words, not the unchanged Ctrl/Mod key names or whole multi-line prefixes.
  • Transfers: move to a hunk, use :diff-get, undo, then :diff-put and undo in the destination. The intended hunk changes; neither action saves.
  • Inline: :diff-off, then launch "$HX" --diff --diff-layout inline ../before/src/lib.rs src/lib.rs. Edit working text, navigate hunks and undo. Deleted baseline rows stay virtual; saving the working file must not insert deleted text or alignment rows.
  • Changeset: :dr (Space g r) shows changed/added/deleted/renamed paths. Switch files, change inline/split layout and edit multiple working files. Edits remain when switching; baselines stay read-only. Git rename entries may appear as add/delete; JJ uses native rename handling.
  • Refresh/exit: with a review open, externally add/change a fixture file. Catalog/clean files refresh; dirty buffers survive. :diff-off keeps the working file on the left, removes comparison panes, restores the prior sidebar state and retains all unsaved buffers/unrelated panes.
  • Three-way: launch "$HX" --diff3 ../three/left.rs ../three/base.rs ../three/right.rs. Base is centered; outer panes align with it. Transfer a hunk between a focused outer pane and base; undo. Exit while an outer pane is focused: that variant survives.
  • Diff folds: :diff-fold 0 hides unchanged context in split, inline and three-way views. :fold-open expands paired context; search into hidden text reveals it. Editing/undo opens invalidated folds; saving contains full source.
  • Code folds: outside comparisons, use z f t, z f T, open an enclosing/ nested fold, search into it, and try :fold-selection on plain text. Folding is view-local; editing invalidates stale folds, and saves never omit hidden text.

4. Pager, patches, JJ and jjui

  • Pager: "$HX" --pager src/lib.rs, then git show HEAD:src/lib.rs | "$HX" --pager --language rust. Both highlight; movement/search/yank work. Insert, undo, write/save-as and move cannot mutate files. q exits cleanly. Piped input waits for EOF; follow/ANSI-man support is not expected.
  • Large file: "$HX" --pager ../large.txt; record first-paint latency/RSS, search near EOF and exit. It loads the complete input, not bounded streaming storage; do not confuse that limit with failed small-file pager behavior.
  • Both patch formats: open ../patches/git.patch and ../patches/jj.patch with "$HX" --patch PATH, in inline and --diff-layout side-by-side layouts. Navigate files/hunks; all patch text stays read-only and referenced source paths are never opened for editing. Also pipe each producer to "$HX" --patch.
  • Native JJ: from $TESTROOT/jj, open src/lib.rs; trust the workspace. Space g g finds changed files, including when Helix starts outside the repo and opens an absolute file path. :jjr selects revisions: @ is editable, the parent is read-only; switching revisions retains layout and unsaved buffers. Sidebar r reopens the revision picker. No checkout/history rewrite occurs.
  • jjui display: with your configured tools, browse several previously unseen revisions. Preview is inline, full diff is split; colors match your theme and long lines wrap. No binary garbage, broken terminal state or stale prior revision.
  • jjui editing: only in the JJ fixture, use Shift-E / jj diffedit through your configured Neohelix editor. Save a deliberate edit, exit and confirm jjui returns and JJ imports it once. This can rewrite revisions/rebase descendants.
  • Performance: compare matched Delta/Neohelix layouts, widths and revisions using the benchmark harnesses. Record stopped-worker/ empty-cache startup, first unseen diff after initialization, and revisit separately. The target is within 50 ms of Delta in the stated matched case, not a universal guarantee. Use private benchmark caches; do not clear your normal caches.

5. GitLens, blame and media

  • Local blame: on a committed fixture line, Space B opens compact details. Near the screen bottom it expands upward. y copies the hash; d, then d returns from full diff with scroll/selection retained. This repo has no remote: local details should work without a token. Space g b independently toggles a theme-colored blame gutter that remains aligned while scrolling and editing.
  • Inline blame: temporarily enable inline-blame.auto-fetch, then test :set inline-blame.show cursor-line, all-lines and never. Placement follows the selected mode; record scrolling lag rather than assuming fetching is free. Restore never and your prior auto-fetch value afterward.
  • GitHub/GHE: on a known committed line in a trusted real repo, inspect verified PR details; Tab/Shift-Tab select commit/PR links, c copies and Enter opens the selected URL. A fork must not redirect validated upstream PR URLs to origin. With an environment token, no Keychain prompt should be needed. Offline/ failed lookup keeps local details and labels unverified hints honestly.
  • Cache invalidation: revisit a line after its responsible commit changes in the fixture; blame reflects the new commit, not the old PR. Unsaved/uncommitted text is not falsely attributed to an unrelated commit. :gitlens-clear-cache clears saved PR details.
  • Media: launch Helix from $TESTROOT/media; picker-preview sample.png and a multipage PDF you copy there. With pdftoppm installed, pages fit, page scrolling works and rapid selection changes do not leave old images behind. Repeat in patched Zellij. Unsupported terminals/missing tools show a fallback, not garbage. Ordinary document opening is not a dedicated image/PDF viewer yet.

6. Shared LSP: two actual editor processes

Open the same fixture workspace and file in two panes using the same binary, config and effective environment. Trust it in both; disable both autosave modes. Rust-analyzer must be installed. Use OS process inspection to distinguish this workspace’s backend from other projects and Neohelix’s small proxy/broker helpers.

  • Sharing/default: both have completion, hover and diagnostics, but only one rust-analyzer backend. The second editor avoids a second full index.
  • Unsaved sync: type in A; B updates before any disk write, with independent cursor/scroll. Type in B, undo, and try interleaved inserts. Both converge; use git diff/disk inspection to verify this is not filesystem reload.
  • Workspace edits/save: LSP-rename greet across the two Rust files while one has unsaved peer edits. Both update once without losing those edits. Move a file using Helix: the peer path follows without saving its contents. Save matching text: the peer’s modified marker clears only if its text matches that save.
  • Lifetime/isolation: close A; B’s LSP still works. :lsp-restart in B starts a private backend without disturbing another editor. In a fresh session with lsp.shared = false in both configs, each editor gets an independent backend. Restore your config afterward; closing all fixture editors reaps their backends.

Skip optional external integrations explicitly rather than marking them passed. Keep performance numbers separate from functional results. Use the linked guides for limits: workspace edits are not globally atomic, arbitrary external renames are not tracked, and native macOS is not validated merely by a Linux test run.

Neohelix review cheat sheet

For actions paired with expected results and disposable fixtures, use the acceptance walkthrough.

See the optional user keymap and short command aliases for the author’s Space g and z f menus. Tables below also include fork defaults.

Start a review

hx --review                         # Git HEAD / JJ parent vs working copy
hx --review before-dir after-dir    # Full directory changeset
hx --diff before.rs after.rs        # Two editable source files
hx --diff3 left.rs base.rs right.rs  # Three editable files, base in the middle
hx --diff --diff-layout inline before.rs after.rs
git diff | hx --patch
jj diff --color-words --color never | hx --patch

File paths select the normal Helix language/Tree-sitter configuration. Patches accept Git unified and native JJ markers, are read-only, and never open paths named inside the patch. Inline file/review views edit the real working document; deleted baseline rows are virtual and read-only. --pager makes file inputs read-only.

Sidebar navigation

/ edits a live, case-insensitive name/path substring filter. Matching files remain in their hierarchy with ancestors revealed; Enter keeps the filter, then opens the selected file on the next press. n/p (or N backwards) wrap through matches without switching the review file. Esc cancels an edit, clears an accepted filter, then returns to the editor on a subsequent press. Backspace edits a grapheme; Ctrl-u clears the input and Ctrl-w deletes a word. H/L collapse/expand all; PageUp/PageDown and Ctrl-u/Ctrl-d navigate pages and half-pages outside filter input. ? shows a key summary. Clearing the filter restores browsing expansion; refresh retains the query and selection.

j / k select; h collapses or goes to parent; l expands; Enter opens a file or toggles a directory. g / G select first / last. Tab or Escape returns to editing. r refreshes ordinary/Git trees, but reopens the revision picker in a JJ review. Without a filter, review-tree n / p change file and v toggles layout. :file-tree-close closes the sidebar without closing documents.

Colors and word changes

Diffs keep normal Helix gutter icons and syntax foreground colors. Muted line backgrounds show additions/removals; stronger word backgrounds emphasize changed tokens within replacement blocks. This works in split, inline, three-way and patch views. Large replacement blocks fall back to line-only coloring.

Theme overrides: ui.diff.minus, ui.diff.plus, ui.diff.minus.word, ui.diff.plus.word (set bg, not the syntax foreground). Word highlighting is textual, not a compiler-semantic analysis.

Picker readability

The active diagnostic message wraps within its picker column instead of being hidden behind the preview. Alt-] / Alt-[ scroll long messages; moving to a different diagnostic resets the scroll. File previews show a loading state until asynchronous Tree-sitter highlighting resolves, with plaintext fallback if no parser is available.

PNG/PDF picker previews work in direct Ghostty/Kitty sessions. PDFs require pdftoppm; Alt-j / Alt-k change pages. See media previews for limits and current multiplexer support.

Steel configuration and plugins

Neohelix includes Steel by default. TOML remains supported, but neither a global config.toml nor languages.toml is required for a Steel-only setup. Your config normally lives in ~/.config/helix/ (%AppData%\helix\ on Windows), outside the checkout.

A minimal setup

Put reusable definitions in helix.scm, with an exported installer:

;; ~/.config/helix/helix.scm
(require "helix/configuration.scm")
(provide configure!)

(define (configure!)
  (mouse #f)
  (line-number 'relative)
  (cursor-shape #:normal 'block #:insert 'bar #:select 'underline)
  (lsp (hash 'display-inlay-hints #t)))

Call it from init.scm:

;; ~/.config/helix/init.scm
(require "helix.scm")
(configure!)

This separates importing definitions from applying settings. Larger configs can split editing, appearance, languages and keybindings into modules, export an installer from each, and call them from the entry point. Explicit imports and prefix-in help avoid name collisions.

Named helpers and structured settings

The public helix/configuration.scm module provides helpers such as mouse, statusline, cursor-shape, define-lsp and define-language. Structured settings still use hashes; Scheme does not require everything to be flat or top-level. The additional examples below belong inside configure!, with the module’s helix/configuration.scm import in scope. For options without a suitable helper, use the generic API:

(set-option! "auto-reload" #t)
(set-option! "inline-blame.show" "never")

Some helpers construct whole sections with defaults. To change only one field while preserving other configured fields, use set-option! on that field. For example, statusline has its own default separator, and the whitespace helper fills in omitted render settings.

Shared LSP defaults on for compatible Unix editor processes. Opt out with (lsp (hash 'shared #f)). Changes affect newly started servers; restart the editor to change existing connections.

Languages, servers and formatters

(define-lsp "steel-language-server"
  (command "steel-language-server")
  (args '()))

(define-language "scheme"
  (language-servers '("steel-language-server")))

Language overrides preserve unrelated built-in fields, including grammars and roots. A formatter is another language field: for example, (formatter (command "typstyle") (args '("--wrap-text"))) inside a define-language form for "typst".

Server initialization JSON is different: supplying config to define-lsp or set-lsp-config! replaces the existing initialization JSON. Read get-lsp-config and explicitly deep-merge it to retain built-in server options. Do not unintentionally replace rust-analyzer’s initialization settings.

--health loads user and trusted-project Steel configuration headlessly, so its language-server, formatter and clipboard checks reflect the effective settings. It does not start language servers or enter the terminal UI. Configuration errors are reported instead of silently checking the built-in defaults.

Keybindings and plugins

Load plugin commands in helix.scm and export commands that should be available in command mode. Install global bindings separately in your keybindings module. GitLens is bundled under plugins/gitlens/, but importing it installs no global shortcut. It needs Neohelix’s native bindings, not just any Steel fork.

Use keymap for declarative mappings or add-global-keybinding with a hash for programmatically composed maps and command sequences. The optional user keymap is not the fork’s built-in default map.

Startup layers, trust and reload

Startup loads user helix.scm and init.scm first, then a trusted project’s .helix/helix.scm and .helix/init.scm when both project files exist. Relative imports resolve within their own layer. Explicit project settings override user settings rather than replacing the entire user configuration.

HELIX_STEEL_CONFIG selects a different user config directory; it is unnecessary for the default location and does not bypass project trust. Use :config-open and :config-reload to edit/reload configuration. Refreshes triggered by :workspace-trust also work without a placeholder TOML file. Existing server connections may require an editor restart to adopt new initialization settings.

Trusted Scheme can execute code and perform I/O. Workspace trust still gates project configuration; read-only pager/diff modes are not a plugin sandbox.

Pager mode

Neohelix can browse files and finite piped input using its normal editor renderer, Tree-sitter syntax highlighting, navigation, search, selections, and yank commands.

hx --pager src/main.rs
cat src/main.rs | hx --pager --language rust
git show --color=never | hx --pager --language diff

--pager reads stdin when no file arguments are supplied. An explicit - also selects stdin; do not combine it with file arguments. Files can use the normal file:line:column syntax and --vsplit/--hsplit options. Directories and missing input files are errors rather than opening a picker or a new file.

File inputs use normal Helix language detection. For piped code, select a language with --language <name> or :set-language; --language text disables syntax highlighting. Language names match Helix’s language configuration. There is no external syntax-highlighting engine.

Controls and protection

  • Use normal Helix movement, scrolling, search, selection, and yank commands.
  • Press q in normal or select mode to close the whole pager session without writing or asking about modified buffers. Escape still dismisses prompts/popups.
  • Read-only buffers show the normal [readonly] statusline indicator when that element is included in your statusline.
  • Text-changing transactions, undo/redo, writes (including :write! and save-as), and :move are blocked. Selection-only transactions remain allowed.
  • Documents opened later in the pager session are also read-only. The editing policy is separate from filesystem permissions, and is also used for immutable baseline panes beside editable working files in diff/review sessions.
  • Pager documents do not start language servers or VCS diff providers, or register document-open hooks for automatic watching. Your usual theme, syntax definitions, keymaps, and trusted Steel startup configuration remain available.

Read-only protects editor buffer mutations and saves. It is not a sandbox for explicit shell commands or trusted plugins that perform their own filesystem I/O.

When stdout is redirected, --pager copies input bytes directly to stdout instead of starting the terminal UI. This preserves encoding and avoids emitting UI escape sequences into a downstream pipeline.

First-milestone limits

Piped input is loaded to EOF before browsing starts. Live streams/follow mode, bounded streaming storage, ANSI color interpretation, and man-page overstrike handling are future work. This is not yet a drop-in replacement for every less use case.

Terminal controls in read-only document text are rendered visibly rather than executed; the underlying text and Tree-sitter offsets are unchanged. For best results, request uncolored output from producers such as Git in this milestone.

An example opt-in shell setting for finite, plain-text command output is:

export PAGER='hx --pager'

Do not set MANPAGER or a terminal scrollback pager expecting ANSI/overstrike support yet.

Editable side-by-side file comparison

For full changesets and the reusable expandable sidebar, see changeset review and file tree.

hx --diff before.rs after.rs

Inside Helix, :diff-split other.rs compares the current file with another; :diff-split before.rs after.rs opens both. Both panes are normal editable documents, with path-based language detection and Tree-sitter syntax colors. Use the normal Ctrl-w h / Ctrl-w l window commands to switch panes. :diff-split reuses existing side-by-side panes in the focused row, creating only missing columns. Other rows and displaced buffers are preserved. Add --pager to browse both files read-only, with q to close the viewer. The gutter uses Helix’s configured added/deleted/modified icons and theme styles, just like normal editing—not literal +/- signs. Replacements have the modified marker on both sides; empty hunks retain boundary markers.

Deleted/left lines have a removal background; added/right lines have an addition background. Defaults are Delta-like dark red/green fills (pale red/green on light themes), including when the editor background is transparent. Themes can override them with "ui.diff.minus" = { bg = "#300000" } and "ui.diff.plus" = { bg = "#002800" }. Explicit backgrounds in diff.minus and diff.plus are also honored; bright foreground/gutter colors are never used as background fills. Syntax foregrounds remain unchanged.

Replacement hunks also emphasize changed words with a stronger, muted background, while retaining Tree-sitter foreground colors. This applies to split, three-way, inline and patch views, including --render-diff output. Themes can override ui.diff.minus.word and ui.diff.plus.word with background colors. Unicode word boundaries are used. Pure additions/deletions keep the line fill. Replacement lines are paired before refinement, so matching words on another line cannot swallow unchanged key names or create cross-line word emphasis. Replacement blocks above 128 lines, 16,384 characters on either side, or 2,048 tokens fall back to line-only highlighting to bound refinement work. This is textual word diffing, not compiler-aware semantic equivalence.

Blank alignment rows are virtual: they never become file contents. Scrolling either focused pane synchronizes the other’s aligned position. Diff computation runs in the background and stale results are hidden while edits are recomputed. Switching panes brings an offscreen single cursor to the corresponding source location; existing visible cursors and multiple selections are preserved.

An empty side of a hunk is addressed at the following line, or at EOF for trailing changes. If the diff is still updating, transfer/navigation commands ask you to retry.

Folding unchanged context

Use :diff-fold to focus on changes without changing the underlying files. :diff-fold 5 retains more context; :diff-fold 0 shows just changes and fold summaries. Runs shorter than two hidden lines remain expanded. Collapsing is explicit, not enabled by default. It works in two-pane, three-way and editable inline comparisons, and read-only inline patch views. Multi-file reviews use the same commands for the current file; collapse again after switching files.

Summary rows retain the real source line number. Normal up/down movement skips folded text, and :fold-open opens the summary at the cursor. Search/goto targets inside hidden lines reveal their fold. Compared panes open/collapse together, preserving alignment and inline deleted-row highlighting. Folds containing an existing cursor stay open. Edits (including undo, reload and hunk transfers) currently open all folds in the comparison; use :diff-fold again after the updated diff is ready. This conservative invalidation prevents stale ranges from hiding newly changed text.

Outside diff mode, select lines and run :fold-selection to use the same view-local folding mechanism; :fold-open and :fold-open-all also work there. Fold commands do not modify text, and save writes the complete file. Selections, operators and clipboard actions still address real text, including hidden lines when a selection spans a fold. Normal views also support nested Tree-sitter code folding. No default keys are taken over; the commands can be bound in TOML or Steel like other commands.

One comparison session (two or three panes) is supported per editor. Closing a compared pane or switching its buffer ends the comparison. Comparison panes temporarily disable soft-wrap and inline diagnostic rows to preserve logical-line alignment; other views keep their settings. Long lines can be scrolled horizontally. Arbitrary Git/JJ revision inputs and GitLens integration are not implemented.

Three-way comparison

hx --diff3 left.rs base.rs right.rs
hx --diff3 --pager left.rs base.rs right.rs

Inside Helix, use :diff-three left.rs base.rs right.rs (alias :diff3), or give :diff-split three paths. Existing columns in the focused row are reused; only missing columns are created. Files are ordered left | base | right. All three retain normal editing, syntax highlighting, undo and explicit saves; --pager makes all three read-only and q exits.

Both variants are compared independently against the middle base. Alignment combines insertion gaps from both comparisons; scrolling any pane synchronizes the other two. Base lines changed by either variant have removal backgrounds; changed variant lines have addition backgrounds. Normal Helix gutter icons remain in use. :diff-next / :diff-prev navigate the focused variant’s changes, or the union of both comparisons when focused on base.

From an outer pane, :diff-get copies the base hunk into that variant; :diff-put copies that variant’s hunk into base. These are undoable edits, never automatic writes. Transfer commands in the base pane require choosing an outer pane first, rather than guessing a variant. Editing base recomputes both comparisons. :diff-off keeps the focused outer variant (or the right variant when base is focused) in the leftmost comparison pane and closes the other comparison panes. All buffers, including unsaved edits, remain available. This is a three-way comparison/editor, not an automatic merge or conflict resolver, and requires three complete files (not partial patch input).

Interactive inline viewing

hx --diff --diff-layout inline before.rs after.rs opens the real after.rs document for editing, with removed baseline lines rendered as virtual, read-only rows before the corresponding working lines. Movement, selections, search, LSP, undo and saves operate on the working file, not synthetic patch text. Deleted rows retain syntax highlighting from the complete baseline source tree and use the normal configured gutter icons. They are not cursor/edit targets. :diff-next / :diff-prev navigate hunks; :diff-get restores a baseline hunk into the working file as an undoable edit. :diff-put is rejected because the inline baseline is read-only. Nothing is saved until :write.

Add --pager for a strictly read-only synthetic presentation in which both old and new text are searchable/selectable and q exits. Raw patch input remains read-only too: partial patches do not provide a complete save target.

Read-only rendering: standalone and jjui

hx --render-diff before.rs after.rs
hx --render-diff --diff-layout inline before.rs after.rs
hx --render-diff --color always --diff-layout inline before.rs after.rs | less -R
hx --render-diff --width 120 before-directory after-directory

This emits flow text without acquiring a terminal. Both layouts use the same comparison model and Helix’s native document renderer/Tree-sitter highlighting from each complete source document. Inline output shows old/new line numbers and all removed lines before added lines in a hunk. Output contains only text and optional SGR color/style codes: never cursor positioning, alternate-screen commands, OSC clipboard sequences, or controls from input text.

Options: --color auto|always|never, --width 20..4096 (default 100), --diff-context 0..1000 (default 3), and --diff-theme <name>. Long lines are soft-wrapped using Helix’s native text layout. Inline output wraps at the available text width; split output wraps each side independently and pads the shorter side to keep the next logical source lines aligned. Continuation rows retain syntax, line and word-diff colors, with blank line-number gutters. Directory inputs are compared recursively in sorted order. Symlinks are reported without following them; binary files, empty-file additions/removals, executable-bit changes and missing final newlines are reported explicitly. Input files are never written.

The formatter loads the normal built-in/TOML settings, then user Steel configuration followed by trusted project Steel configuration. Themes (including dynamic themes), icons and language overrides therefore match the editor. --diff-theme <name> overrides the configured theme. No terminal is acquired and no editor event loop, LSP or file-watching service is started. Ordinary Scheme display output goes to stderr, not into the diff stream. Normal Steel cache/module initialization and trusted configuration side effects still apply; this is not a sandbox for startup scripts. Set editor.enable-steel = false in TOML to disable Steel configuration just as in the editor.

Direction: standalone viewer and external hosts

The intended end state is a standalone diff viewer/editor, not just an editor command: side-by-side and inline layouts, a changed-file list, revision/range inputs, history navigation, and eventually conflict-resolution layouts. These include development targets beyond the current editable side-by-side UI and read-only side-by-side/inline formatter. Diffview.nvim is a workflow reference, not a requirement to reproduce its UI or Git-specific implementation.

Both layouts should share the comparison model and retain Tree-sitter syntax from the source documents. File inputs can be editable. A patch received over stdin must remain a read-only review unless complete backing documents have been explicitly supplied: omitted context is not a complete file and must never be written back as one.

External integration has two separate contracts:

  • Formatter: consume files or a patch and emit styled text for a host’s own read-only diff view; the host handles navigation. This must not initialize a terminal UI, issue cursor/alternate-screen commands, or execute input controls.

In jjui 0.10.11, the built-in diff viewer captures command output and renders it as text (diff source, command runner). Its interactive command runner uses a separate process-launch path. Therefore read-only styled output can use the formatter route; embedding Helix editing requires an interactive host integration, not only a ui.pager setting. The formatter contract is implemented by --render-diff; full-terminal handoff uses jjui’s existing interactive runner. In-screen interactive terminal embedding would still require host support. Current non-terminal --pager output is still byte-preserving passthrough (except explicit patch formatting). Sources and boundaries

Git reviews compare HEAD with working files and include staged, unstaged, deleted and untracked paths. Index-only/metadata changes receive a summary. Git renames currently appear as deletion/addition entries. JJ uses its native working-copy/parent comparison, including unsnapshotted files and rename paths. Catalog reads use native VCS APIs, not shell commands, and respect workspace trust. They do not stage files or change HEAD/the JJ operation history. JJ repositories require explicit workspace trust: run :workspace-trust, then :diff-review if opening an unfamiliar workspace.

Directory review treats the left side as baseline and the right as working files. Missing files, symlinks, binary and special files get read-only snapshots/summaries; symlinks and special files are never read as ordinary source files. Added text files are editable. With file watching enabled, review catalogs and inline snapshots refresh automatically after a 250 ms debounce. Additions/deletions, saved patch changes, Git refs/index and JJ operation heads are included; object stores are excluded. Explicit directory comparisons watch both selected roots even outside a workspace, without watching the caller’s whole directory. Refresh is bounded to one automatic catalog worker with a pending follow-up; it preserves dirty buffers, active file, focus and sidebar selection/expansion. :diff-review-refresh remains a fallback when watching is disabled or unavailable. A piped patch is immutable; reopen with new input instead of refreshing it.

Unchanged context can be folded per file in split and inline layouts; see folding commands and editing behavior. This is the first multi-file review layer, not yet a complete Hunk/Diffview-style VCS interface. A native JJ revision selector now drives the same sidebar and review panes. A persistent revision graph, history-changing operations, staging and a continuous multi-file changeset view are not implemented. Input is finite and catalogs retain source snapshots in memory; this is not a streaming viewer for arbitrarily large changesets. Use JJ’s external diff-tool integration to select revisions/ranges and pass complete files to Helix.

The generic Files tree implements expansion/collapse, navigation, opening files, ignore filtering and layout reservation. It does not yet implement file creation, rename/move/delete, filesystem-tree Git status badges or persistent filesystem-tree auto-refresh. Those are separate from review-catalog watching and from the toggleable per-line blame gutter.

Native JJ review workspace

The first slice is a native revision selector connected to Neohelix’s existing changed-file sidebar and inline/split diff editor. It runs inside the editor, using jj-lib; no jj subprocess, terminal embedding, or renderer daemon is used. It is not yet a full jjui replacement or a persistent revision-graph panel.

Try it

Open a file inside a trusted JJ workspace, then run:

:jj-review

The picker shows the change ID, commit ID, bookmarks, author, and description. @ marks the current working revision. Search and select with the normal picker keys; Enter opens its changed files in the review sidebar. Full commit IDs, not ambiguous change IDs, identify historical snapshots, including divergent changes.

An optional revset narrows the list, for example:

:jj-review @
:jj-review ancestors(@, 20)
:jjr bookmarks()

The default is @ | ancestors(@, 50) | bookmarks(). The list is limited to the first 200 revisions in JJ’s reverse-topological order. Configured revset aliases are supported. An invalid revset or an untrusted/non-JJ workspace reports an error without replacing the existing review.

The active file supplies repository context even if Helix started outside that repository. When revisiting the picker from a review snapshot, the sidebar’s repository supplies context instead. In a JJ review sidebar, r reopens the default revision selector.

Editing and navigation

  • Selecting @ opens the existing working-copy review: the working side is editable and reuses unsaved buffers. It includes working changes not yet recorded by a separate jj invocation.
  • Selecting a historical commit opens immutable before/after snapshots. They are deliberately read-only: selecting history neither checks out the revision nor writes historical contents into today’s working files.
  • Existing file navigation, hunk navigation, word coloring, syntax highlighting, wrapping, and :diff-layout inline / :diff-layout side-by-side remain available. Switching revisions preserves the layout and reuses the review panes.
  • :diff-off exits the review and restores the previous filesystem sidebar.

Historical comparisons use a commit’s merged parent tree as the baseline, as native JJ diffs do. Renames and conflict materialization use the existing native JJ provider. Historical views do not follow working-file changes. Reopening the revision selector reads the current operation head afresh; it does not reconcile divergent operations, rewrite commits, or change bookmarks.

Next steps

A persistent revision graph/list beside the file tree, selection-driven previews, and explicit JJ edit/new/rebase operations are not implemented yet. Those need buffer-safety checks, transactional error handling, and refresh/selection rules. Keeping the editor open amortizes configuration and grammar/query initialization; it does not eliminate parsing costs for previously unseen source contents.

Performance and caching

Local metadata is native and loaded in a background worker. GitHub enrichment uses native Octocrab HTTP with your existing GitHub authentication, a five-second timeout, no shell interpolation, bounded output, and a five-minute/128-entry persistent cache. Only Shift-B initiates a plugin lookup; no plugin network work runs on startup or render. Saved metadata survives editor restarts; stale details remain visible while refreshing, for up to seven days. The cache is lazy-loaded on the first request, stored in Helix’s cache directory under plugins/gitlens-pr-v1.json (normally $XDG_CACHE_HOME/helix/plugins/gitlens-pr-v1.json, or ~/.cache/helix/plugins/gitlens-pr-v1.json on Linux), and contains metadata only, never authentication tokens. Unix files are mode 0600; private repository titles may be present. Run :gitlens-clear-cache to discard saved details. The existing inline-blame.auto-fetch setting is independent of this plugin. Enrichment preserves selection and scroll position. Replies for changed documents/versions/cursor lines are ignored, and late replies cannot reopen dismissed popups or replace a diff view you have already left.

Origin is preferred for actual commit lookups and commit links. Upstream provides original commit-message PR hints in forks. Up to 20 associated PRs are displayed using the commit-to-PR API.

Older cache records with rewritten links are invalidated automatically. Confirmed unpublished commits omit the dead commit link; publishing the branch makes that hash available on GitHub.

The PR cache holds 128 repository–commit pairs total, not 128 lines. Lines sharing a commit share an entry. Shared LSP instances

Status: experimental Unix implementation, enabled by default. Set editor.lsp.shared = false to use ordinary independent language servers. Review the restrictions below for your workflow. Native macOS runtime testing is pending. The target is independent Neohelix processes, including separate Zellij panes; sharing must not depend on the terminal multiplexer.

In Steel configuration:

(require "helix/configuration.scm")
(lsp (hash 'shared #f)) ; opt out of sharing

Or in TOML:

[editor.lsp]
shared = false # opt out of sharing

Changes apply to newly started language servers; already attached servers are not migrated. Close and reopen the editor to switch an existing workspace. :lsp-restart deliberately starts a private server without disturbing peers. The former HELIX_SHARED_LSP opt-in is no longer used.

Behavior and restrictions

Compatible Neohelix processes opening the same or different files in a workspace can share a server. Each editor owns a small stdio proxy; a private Unix-socket broker owns the actual language server. These helpers skip configuration/Steel initialization and use single-threaded asynchronous I/O runtimes.

  • The broker remaps request IDs, cancellation and progress tokens. Document diagnostics go to synchronized views, with their local versions translated; diagnostics for unopened files can go to all attached editors. Watcher notifications come from one frontend at a time; registrations are replayed to peers and pending registrations survive leader departure.
  • A file has one authoritative unsaved document. Typing in either editor updates the other through version-checked transactions, without saving or reloading from disk. Cursors, selections and scroll positions remain independent. Incremental edits are transformed using their actual operations; full-text changes use Unicode-aware differences. Simultaneous typing can interleave characters. This is text coordination, not semantic merging. A clean newly opened buffer joins the existing unsaved contents. A preexisting divergent edited buffer instead isolates, preserving both versions.
  • Peer changes do not echo back into the same server. Each view has at most one pending synchronization request per file; newer changes coalesce behind it. Saving clears a peer’s modified marker only if its version/text still match what was saved. Moving a file or directory inside Helix rebinds peer buffers while retaining text and selections. This does not promise tracking arbitrary external filesystem renames.
  • Normal navigation, completion, diagnostics, formatting, semantic tokens, symbols, folding, rename, code actions and execute-command requests are routed. Workspace edits carry one-shot, expiring version-check tokens. The requesting editor applies its files; the broker applies edits for peer-only open files to their shared unsaved documents. Closed files use the requesting editor’s normal workspace-edit path. Server-initiated workspace edits choose one driver, not every window. File creation and rename operations use that driver too.
  • Stale versions, overlapping edits, repeated sequential edits to one shared file, creating/deleting an open shared file, and destination-buffer collisions are rejected. Workspace edits are not globally atomic: if a peer changes after preparation, local edits may already be applied. Inspect or undo those before retrying. A driver disconnect never replays a potentially applied edit to a peer. Unknown extensions still isolate before execution; retry the cancelled request after isolation. Mutating requests are never automatically replayed. User prompts/show-document requests are not broadcast.
  • Changed effective settings also cause isolation. Backend failure cancels pending requests and starts independent servers with each frontend’s unsaved buffers. Requests need retrying. Fallback requires unchanged capabilities; otherwise restart the LSP explicitly. Buffer text remains in Helix.
  • :lsp-restart starts a fresh private server for the current editor. It neither reattaches to the old backend nor restarts another editor’s server. Exiting one editor leaves surviving peers running. Exiting the last attached editor shuts down/reaps the backend and removes the socket (with a bounded two-second graceful shutdown before forced cleanup); no unwatched workspace index is retained for a future session.

This is an editor-aware protocol, not a transparent multiplexer for arbitrary LSP clients. Read-only views that cannot accept synchronization and other incompatible frontends fall back rather than pretending their text is synchronized. Custom servers with pane-dependent environments may not share; disable sharing if independent editor-local state is required.

Compatibility, discovery and bounds

Compatibility hashes include the resolved executable and its filesystem identity, arguments, canonical workspace directory, effective server environment, complete initialize parameters except editor PID, and broker/editor identity. Capabilities, initialization options, root URI and workspace folders must match. Settings are also checked when delivered after initialization. Mutable scripts or server dependencies referenced by arguments are not recursively fingerprinted; restart after changing those. No configuration or credentials are written to socket metadata or logs.

Presentation-only _, SHLVL, OLDPWD, COLUMNS, LINES, and ZELLIJ_PANE_ID are removed from both identity and the server environment. PWD is the canonical workspace directory. Other environment differences conservatively prevent sharing. Workspace trust stays enforced by normal Helix server startup; the broker does not run a second workspace-config loader.

Sockets default to /tmp/neohelix-lsp-<uid>; HELIX_SHARED_LSP_DIR can select another short absolute directory. Directories must be owned by the user with mode 0700, sockets use 0600, peers must have the same effective UID, lock files reject symlinks/hardlinks/public permissions, and startup uses exclusive locks. The shared wire protocol is separate from the diff worker. It supports Linux and macOS peer-credential APIs; native macOS remains unverified.

Limits are 8 brokers per discovery directory, 8 clients per broker, 16 MiB messages/control frames, bounded queues, 1024 outstanding routed requests, 256 registrations and 128 pending server requests. Replay retains up to 512 documents/8 MiB of current document snapshots per frontend; exceeding replay capacity switches that frontend to a private backend without dropping the triggering notification. Incremental and peer changes are compacted into replayable full-text opens, so ordinary typing does not exhaust a growing edit log. Workspace-edit tokens are bounded to 128 and expire after 60 seconds. An oversized/malformed wire message closes the affected transport; Helix retains its buffers, but the LSP may need restarting. Slow readers are disconnected, upstream writes time out, and initialization has a deadline. Never treat these limits as support for arbitrarily large documents.

An unused startup broker expires within the default 120-second idle budget (HELIX_SHARED_LSP_IDLE_SECS, bounded to 1–3600); initialization has its own 60-second deadline. These do not extend the last-attached-client lifecycle.

PNG and PDF picker previews

In Ghostty or Kitty, open a file picker (Space f or Space e) and select a .png or .pdf. The existing preview pane displays the image instead of binary text. File extensions are case-insensitive. No Steel plugin is needed.

PDF previews require pdftoppm on PATH (Poppler’s command-line utilities; poppler-utils on Nix, poppler on Homebrew). PNG previews need no external tool. Neohelix does not link Poppler. Each requested PDF page is rasterized in a child process, without shell interpolation or temporary output files.

Alt-j / Alt-k (or Shift-Down / Shift-Up) select the next / previous PDF page. Other preview scrolling keys also move one page at a time for PDFs. Selecting a different picker entry resets to page one. A page beyond the document’s end shows an error; go back a page to recover. Encrypted/invalid PDFs and missing tools show an explanation rather than raw process output.

Behavior and limits

  • Conversion starts after a 150 ms selection debounce and runs off the UI thread. Changing files/pages or closing/hiding the preview cancels pending work and kills its renderer child. At most two media workers run at once.
  • PDF conversion has a ten-second timeout, 16 MiB output and 16 KiB stderr limits, and rasterizes only the requested page, at up to 1600 pixels on its longest edge.
  • Inputs must be regular files up to 64 MiB. PNG data is limited to 16 MiB and 32 megapixels. PDF page requests are limited to the first 10000 pages.
  • Each picker keeps at most eight cached images, within a 32 MiB encoded-data budget, plus its active preview. Cache identity includes path, size, modification time and page. Revisiting an entry checks that identity; an active preview is a snapshot, not continuously reread on each frame.
  • The transport uses Kitty Unicode placeholders in direct Ghostty and Kitty sessions. The Neohelix-compatible Zellij fork also supports them: its server sets ZELLIJ_KITTY_UNICODE_PLACEHOLDERS=1 in new panes after interpreting placeholders itself (based on Zellij PR #5531). Restart the server after updating; updating only the client does not upgrade an existing session. Do not set this variable manually on stock Zellij. Tmux and unpatched Zellij show a fallback message. Other protocols are not implemented.
  • Images fit the available rectangle while retaining their aspect ratio. Rendering uses at most 128 columns by 128 rows. Placeholder cells participate in the normal compositor, so overlapping UI erases them normally. Terminal image data is freed when the preview disappears; only Neohelix’s own image IDs are deleted.

Opening a PNG/PDF as an ordinary document is unchanged for now. This is a preview-first implementation, not a PDF text editor. The asynchronous provider and native image transport are reusable by a future dedicated read-only pane.

Diagnosing a Zellij-only preview stall

If direct Ghostty works but a picker stops repainting inside Zellij (and Escape recovers), do not assume PNG decoding is blocking the editor. Run hx -vv --log /tmp/neohelix-png.log inside the affected session, select a small PNG, try changing the selection, then close the picker. The log records media read/encoding time, upload dimensions and terminal-write time. A fast load and write with stalled painting narrows the problem to the multiplexer/host path; it does not prove the live terminal renderer works just because a unit test passes.

For a temporary text-only fallback in Zellij, launch env ZELLIJ_KITTY_UNICODE_PLACEHOLDERS=0 hx. This disables image previews for that process without changing your config or the Zellij server.

Watching files and safe reloads

Reusable flow-diff worker

On Unix, file or directory comparisons with hx --render-diff can optionally reuse a private background renderer by setting HELIX_DIFF_WORKER=1. The default is a fresh process with validated disk caches, without a worker. The first request still initializes Steel and parses its documents. Later requests reuse evaluated configuration, language resources and unchanged parsed documents, including when jj exports them under different temporary paths.

The worker now renders files in parallel and retains syntax trees separately from displayed styles. Changed revisions can incrementally update those trees even when hunk coverage or snapshot paths change. Complete outer syntax and local scopes remain available; selected injection groups retain all their source ranges. See the matched measurements.

To initialize a renderer before the first diff, explicitly run this from the same workspace, environment and viewport width used by the formatter:

hx --diff-worker-warm --width 160
HELIX_DIFF_WORKER=1 jj diff

Warmup evaluates configuration and renders unrelated tiny Rust/Markdown inputs; it does not preload the revision you will view. It produces no output and does not enable worker use globally. Widths have separate workers. Normal editor startup does not automatically perform this warmup. A stopped worker’s first diff still pays initialization costs; report that separately from unseen diffs after initialization.

Controls

  • HELIX_DIFF_WORKER=1: opt in to the background renderer.
  • HELIX_DIFF_WORKER=0 (or unset): fresh-process rendering with disk caches.
  • HELIX_DIFF_WORKER_SHARED_VIEWPORT=1: opt into the viewport-independent configuration contract above; default workers remain width/env isolated.
  • HELIX_DIFF_CACHE=0: bypass native configuration and query-analysis disk caches and source highlight events, evaluating configuration and syntax afresh.
  • HELIX_DIFF_HIGHLIGHT_CACHE=0: bypass only source highlight events, retaining native configuration and query-analysis caches for comparison/profiling.
  • HELIX_DIFF_RENDER_THREADS=1: serial directory rendering for comparison. Largest-first scheduling retains lexical output order and bounds queued output, spilling individual results above 1 MiB to private files.
  • HELIX_DIFF_SYNTAX_CACHE=0: disable the shared in-memory syntax-tree cache.
  • HELIX_DIFF_IMMUTABLE_CACHE=0: disable process-local metadata summaries of protected, non-user-owned Nix store directories. Mutable configuration and symlink chains are still checked live on every request.

  • HELIX_DIFF_CACHE_TRACE=1: report profile hits/misses/rejections and query analysis hits to stderr.
  • hx --diff-worker-stop: stop workers matching the current executable, workspace, configuration and environment, across viewport widths.
  • HELIX_DIFF_WORKER_TRACE=1: report worker use or fallback to stderr.
  • HELIX_DIFF_WORKER_IDLE_SECS: idle timeout, default 120 seconds, clamped to 1–3600 seconds.

Isolation and invalidation

Fresh-process disk caches

On Unix the renderer caches effective rendering settings in $XDG_CACHE_HOME/helix/diff-profile-v1 and Tree-sitter query analysis in $XDG_CACHE_HOME/helix/diff-queries-v1 (normally under ~/.cache). A valid native profile avoids starting Steel; cached queries still undergo ordinary query parsing and predicate validation, but skip expensive grammar analysis. Effective language snapshots retain injection-regex aliases, not just exact language names; they omit LSP commands and root matchers unused by rendering. No source text, syntax trees, final output, API credentials or user commands are persisted. Editor settings are limited to those needed for rendering.

Both caches are bound to the executable, platform, environment, workspace, configuration, trust and runtime-resource metadata. Changes invalidate them. Dependencies are validated at request start. A profile is stored only if the dependency fingerprint remains unchanged across configuration evaluation. Configuration edits concurrent with a cache hit are observed on the next request; cached profiles contain rendering data, not executable configuration. Directories are private (0700); files must be same-user-owned, private (0600), regular, non-symlink files with one hard link. SHA-256 checksums catch corruption. Invalid entries fall back to normal configuration evaluation/query compilation. Profiles are bounded to 32 entries of at most 20 MiB; query analysis to 256 entries of at most 1 MiB. Files are replaced atomically.

diff-highlights-v1 holds content-addressed Tree-sitter highlight events: character offsets and styles, not source text, syntax-tree pointers, terminal output, or diff results. The key additionally binds exact input bytes, detected language and the complete effective theme. A cache hit skips parsing that source but still decodes its current bytes and computes its diff, layout, word changes and wrapping normally. New source contents require parsing the complete outer language; unrelated injected-language groups can be skipped. Style collection is limited to the displayed hunk/context ranges, which also form part of the cache key. Undisplayed lines are not highlighted to fill a cache. Disk serialization/writes happen after the file’s output is flushed. Capturing hosts such as jjui still wait for process exit, so deferring writes alone does not remove their cost. Thus navigating an unseen revision can reuse unchanged files, but does not guarantee a cache hit for its new contents.

Highlight files use the same owner/permissions/symlink checks and checksums, plus embedded key, character-count, ordered-offset and style-index validation. Corrupt entries fall back to live Tree-sitter rendering. At most 256 entries, 128 MiB in total, are retained; each entry is capped at 24 MiB. Sources larger than 2 MiB use the original live-tree path instead of materializing cached events. Ordinary editing and interactive diff panes do not use this cache.

The same limitation on arbitrary Scheme external I/O described below applies to disk profiles: declare external dependencies with HELIX_DIFF_WORKER_WATCH, or set HELIX_DIFF_CACHE=0 when configuration depends on undeclared external state. First cache fills still evaluate Steel and compile queries; cached resource timings are not cold-cache-miss timings.

Optional worker

Workers are partitioned by working directory, executable identity, configuration, environment and initial viewport width. Layout, color, theme and context are request options. Requests are serialized. Socket directories are mode 0700, sockets are mode 0600, and both ends verify same-user peer credentials. Startup is locked and the launcher refuses to start another worker when it observes eight live workers in its socket directory.

Before each render, dependency metadata is checked for user/project configuration, workspace trust, runtime resources and installed Steel modules. Edits, additions, deletions and symlink target changes retire the process; the replacement reevaluates configuration and starts with an empty cache. Untrusted project configuration is never executed by the renderer. The server performs this validation; the client does not duplicate the complete dependency walk. Protected Nix store directory summaries can be reused within the process. Store ownership/write permissions are checked, and symlinks are always followed through the live dependency walk, including links that leave the store and return through a mutable alias. User-owned stores use the ordinary walk instead.

Arbitrary external I/O performed by Scheme configuration cannot be inferred. Add external imports to HELIX_DIFF_WORKER_WATCH, stop the worker after changing other external state, or opt out. Like a running editor, configuration is not reevaluated for every unchanged request.

Input files are reread for every request. Parsed-document reuse verifies exact source bytes and detected language, not only metadata or a digest. Its LRU is bounded to 64 documents and 16 MiB of source text; syntax trees and other process allocations require additional memory. Rendered output and diff results are not cached. The independently bounded shared syntax cache retains at most 64 entries and 8 MiB of source text, with a 512 KiB per-source limit; syntax-tree memory is additional. It verifies exact source/language identity, updates copied trees against complete new source, and falls back to a fresh parse on update failure. Changing recognized highlight scopes clears both in-memory caches.

Failure and cancellation

A complete response is buffered before any bytes reach stdout. Startup, transport or worker-limit failures fall back to one-shot rendering without partial or duplicated output. Configuration/render errors remain errors. Responses above 64 MiB fall back to the streaming one-shot renderer; use HELIX_DIFF_WORKER=0 directly for such unusually large outputs.

Disconnected clients are detected before starting queued work, between file pairs and document parses, and periodically while writing output. An individual Tree-sitter parse already in progress is not preempted.

Workers exit after their idle timeout and remove their socket/PID files. Empty lock files remain in the private socket directory. There is no system service, network listener, or persistent rendered-content cache.

The runtime directory is one below the Helix source, so either export a HELIX_RUNTIME environment variable to point to that directory and add it to your ~/.bashrc or equivalent:

export HELIX_RUNTIME=~/src/helix/runtime

ln -Tsf $PWD/runtime ~/.config/helix/runtime

setx HELIX_RUNTIME "%userprofile%\src\helix\runtime"

💡 %userprofile% resolves to your user directory like C:\Users\Your-Name\ for example.

Multiple runtime directories

When Helix finds multiple runtime directories it will search through them for files in the following order:

  1. runtime/ sibling directory to $CARGO_MANIFEST_DIR directory (this is intended for developing and testing helix only).
  2. runtime/ subdirectory of OS-dependent helix user config directory.
  3. $HELIX_RUNTIME
  4. Distribution-specific fallback directory (set at compile time—not run time— with the HELIX_DEFAULT_RUNTIME environment variable)
  5. runtime/ subdirectory of path to Helix executable.

This order also sets the priority for selecting which file will be used if multiple runtime directories have files with the same name.

Note to packagers

If you are making a package of Helix for end users, to provide a good out of the box experience, you should set the HELIX_DEFAULT_RUNTIME environment variable at build time (before invoking cargo build) to a directory which will store the final runtime files after installation. For example, say you want to package the runtime into /usr/lib/helix/runtime. The rough steps a build script could follow are:

  1. export HELIX_DEFAULT_RUNTIME=/usr/lib/helix/runtime
  2. cargo build --profile opt --locked
  3. cp -r runtime $BUILD_DIR/usr/lib/helix/
  4. cp target/opt/hx $BUILD_DIR/usr/bin/hx

This way the resulting hx binary will always look for its runtime directory in /usr/lib/helix/runtime if the user has no custom runtime in ~/.config/helix or HELIX_RUNTIME.

  • Normal mode: For navigation and editing commands. This is the default mode.
  • Insert mode: For typing text directly into the document. Access by typing i in normal mode.
  • Select/extend mode: For making selections and performing operations on them. Access by typing v in normal mode.

Buffers

Buffers are in-memory representations of files. You can have multiple buffers open at once. Use pickers or commands like :buffer-next and :buffer-previous to open buffers or switch between them.

Selection-first editing

Inspired by Kakoune, Helix follows the selection → action model. This means that whatever you are going to act on (a word, a paragraph, a line, etc.) is selected first and the action itself (delete, change, yank, etc.) comes second. A cursor is simply a single width selection.

Multiple selections

Also inspired by Kakoune, multiple selections are a core mode of interaction in Helix. For example, the standard way of replacing multiple instances of a word is to first select all instances (so there is one selection per instance) and then use the change action (c) to edit them all at the same time.

Motions

Motions are commands that move the cursor or modify selections. They’re used for navigation and text manipulation. Examples include w to move to the next word, or f to find a character. See the Movement section of the keymap for more motions.

Registers

Registers

  • User-defined registers
  • Default registers
  • Special registers

In Helix, registers are storage locations for text and other data, such as the result of a search. Registers can be used to cut, copy, and paste text, similar to the clipboard in other text editors. Usage is similar to Vim, with " being used to select a register.

User-defined registers

Helix allows you to create your own named registers for storing text, for example:

  • "ay - Yank the current selection to register a.
  • "op - Paste the text in register o after the selection.

If a register is selected before invoking a change or delete command, the selection will be stored in the register and the action will be carried out:

  • "hc - Store the selection in register h and then change it (delete and enter insert mode).
  • "md - Store the selection in register m and delete it.

Default registers

Commands that use registers, like yank (y), use a default register if none is specified. These registers are used as defaults:

Syntax aware motions

Moving the selection with syntax-aware motions

Alt-p, Alt-o, Alt-i, and Alt-n (or Alt and arrow keys) allow you to move the selection according to its location in the syntax tree. For example, many languages have the following syntax for function calls:

func(arg1, arg2, arg3);

A function call might be parsed by tree-sitter into a tree like the following.

(call
  function: (identifier) ; func
  arguments:
    (arguments           ; (arg1, arg2, arg3)
      (identifier)       ; arg1
      (identifier)       ; arg2
      (identifier)))     ; arg3

Use :tree-sitter-subtree to view the syntax tree of the primary selection. In a more intuitive tree format:

            ┌────┐
            │call│
      ┌─────┴────┴─────┐
      │                │
┌─────▼────┐      ┌────▼────┐
│identifier│      │arguments│
│  "func"  │ ┌────┴───┬─────┴───┐
└──────────┘ │        │         │
             │        │         │
   ┌─────────▼┐  ┌────▼─────┐  ┌▼─────────┐
   │identifier│  │identifier│  │identifier│
   │  "arg1"  │  │  "arg2"  │  │  "arg3"  │
   └──────────┘  └──────────┘  └──────────┘

If you have a selection that wraps arg1 (see the tree above), and you use Alt-n, it will select the next sibling in the syntax tree: arg2.

// before
func([arg1], arg2, arg3)
// after
func(arg1, [arg2], arg3);

Similarly, Alt-o will expand the selection to the parent node, in this case, the arguments node.

func[(arg1, arg2, arg3)];

There is also some nuanced behavior that prevents you from getting stuck on a node with no sibling. When using Alt-p with a selection on arg1, the previous child node will be selected. In the event that arg1 does not have a previous sibling, the selection will move up the syntax tree and select the previous element. As a result, using Alt-p with a selection on arg1 will move the selection to the “func” identifier.

Pickers

Using pickers

Helix has a variety of pickers, which are interactive windows used to select various kinds of items. These include a file picker, global search picker, and more. Most pickers are accessed via keybindings in space mode. Pickers have their own keymap for navigation.

Filtering Picker Results

Most pickers perform fuzzy matching using fzf syntax. Two exceptions are the global search picker, which uses regex, and the workspace symbol picker, which passes search terms to the language server. Note that OR operations (|) are not currently supported.

If a picker shows multiple columns, you may apply the filter to a specific column by prefixing the column name with %. Column names can be shortened to any prefix, so %p, %pa or %pat all mean the same as %path. For example, a query of helix %p .toml !lang in the global search picker searches for the term “helix” within files with paths ending in “.toml” but not including “lang”.

You can insert the contents of a register using Ctrl-r followed by a register name. For example, one could insert the currently selected text using Ctrl-r-., or the directory of the current file using Ctrl-r-% followed by Ctrl-w to remove the last path section. The global search picker will use the contents of the search register if you press Enter without typing a filter. For example, pressing *-Space-/-Enter will start a global search for the currently selected text.

File explorer

Space-e opens an interactive file explorer for browsing and opening files, rooted at the workspace; Space-. opens one rooted at the current buffer’s directory. Unlike the file picker, the explorer does not ignore most files by default; its ignore behaviour is configured separately in the [editor.file-explorer] section.

Jumplist

Using the jumplist

To help with quick navigation, Helix maintains a list of “jumps” called the jumplist. Whenever you make a significant movement (see next section), Helix stores your selections from before the move as a jump. A jump serves as a kind of checkpoint, allowing you to jump to a separate location, make edits, and return to where you were with your previous selections. This way, the jumplist tracks both your previous location and your selections. You can manually save a jump by using Ctrl-s. To jump backward in the jumplist, use Ctrl-o; to go forward, use Ctrl-i. To view and select from the full jumplist, use Space-j to open the jumplist picker.

What makes a jump

The following is a non-exhaustive list of which actions add a jump to the jumplist:

  • Switching buffers
    • Using the buffer picker, going to the next/previous buffer
    • Going to the last accessed/modified file
    • Making a new file (:new FILE)
    • Opening a file (:open FILE)
      • Includes :log-open, :config-open, :config-open-workspace, :tutor
    • Navigating by pickers, global search, or the file explorer
    • goto_file (gf)
  • Big in-file movements
    • select_regex (s)
    • split_regex (S)
    • search (/)
    • keep_selections and remove_selections (K and <A-K>)
    • goto_file_start (gg)
    • goto_file_end
    • goto_last_line (ge)
    • :goto 123 / :123 / 123G
    • goto_definition (gd)
    • goto_declaration (gD)
    • goto_type_definition (gy)
    • goto_reference (gr)
  • Other
    • Ctrl-s manually creates a jump
    • Trying to close a modified buffer can switch you to that buffer and create a jump
    • The debugger can create jumps as you jump stack frames

Select / extend mode

Accessed by typing v in normal mode.

Select mode echoes Normal mode, but changes any movements to extend selections rather than replace them. Goto motions are also changed to extend, so that vgl, for example, extends the selection to the end of the line.

Search is also affected. By default, n and N will remove the current selection and select the next instance of the search term. Toggling this mode before pressing n or N makes it possible to keep the current selection. Command line

  • Quoting
  • Flags
  • Expansions
  • Exceptions

The command line is used for executing typable commands like :write or :quit. Press : to activate the command line.

Typable commands optionally accept arguments. :write for example accepts an optional path to write the file contents. The command line also supports a quoting syntax for arguments, flags to modify command behaviors, and expansions - a way to insert values from the editor. Most commands support these features but some have custom parsing rules (see the exceptions below).

Quoting

By default, command arguments are split on tabs and space characters. :open README.md CHANGELOG.md for example should open two files, README.md and CHANGELOG.md. Arguments that contain spaces can be surrounded in single quotes (') or backticks (`) to prevent the space from separating the argument, like :open 'a b.txt'.

Double quotes may be used the same way, but double quotes expand their inner content. :echo "%{cursor_line}" for example may print 1 because of the expansion for the cursor_line variable. :echo '%{cursor_line}' though prints %{cursor_line} literally: content within single quotes or backticks is interpreted as-is.

On Unix systems the backslash character may be used to escape certain characters depending on where it is used. Within an argument which isn’t surround in quotes, the backslash can be used to escape the space or tab characters: :open a\ b.txt is equivalent to :open 'a b.txt'. The backslash may also be used to escape quote characters (', `, ") or the percent token (%) when used at the beginning of an argument. :echo \%sh{foo} for example prints %sh{foo} instead of invoking a foo shell command and :echo \"quote prints "quote. The backslash character is treated literally in any other situation on Unix systems and always on Windows: :echo \n always prints \n.

Flags

Command flags are optional switches that can be used to alter the behavior of a command. For example the :sort command accepts an optional --reverse (or -r for short) flag which causes the sort command to reverse the sorting direction. Typing the - character shows completions for the current command’s flags, if any.

The -- flag specifies the end of flags. All arguments after -- are treated as positional arguments: :open -- -a.txt opens a file called -a.txt.

Expansions

Expansions are patterns that Helix recognizes and replaces within the command line. Helix recognizes anything starting with a percent token (%) as an expansion, for example %sh{echo hi!}. Expansions are particularly useful when used in commands like :echo or :noop for executing simple scripts. For example:

[keys.normal]
# Print the current line's git blame information to the statusline.
space.B = ":echo %sh{git blame -L %{cursor_line},+1 %{buffer_name}}"

Expansions take the form %[<kind>]<open><contents><close>. In %sh{echo hi!}, for example, the kind is sh - the shell expansion - and the contents are “echo hi!”, with { and } acting as opening and closing delimiters. The following open/close characters are recognized as expansion delimiter pairs: (/), [/], {/} and </>. Plus the single characters ', " or | may be used instead: %{cursor_line} is equivalent to %<cursor_line>, %[cursor_line] or %|cursor_line|.

To escape a percent character instead of treating it as an expansion, use two percent characters consecutively. To execute a shell command like date -u +'%Y-%m-%d', double the percent characters: :echo %sh{date -u +'%%Y-%%m-%%d'}.

When no <kind> is provided, Helix will expand a variable. For example %{cursor_line} can be used as in argument to insert the line number. :echo %{cursor_line} for instance may print 1 to the statusline.

Aside from editor variables, the following expansions may be used:

  • Unicode %u{..}. The contents may contain up to six hexadecimal numbers corresponding to a Unicode codepoint value. For example :echo %u{25CF} prints ● to the statusline.
  • Shell %sh{..}. The contents are passed to the configured shell command. For example :echo %sh{echo "20 * 5" | bc} may print 100 on the statusline on when using a shell with echo and the bc calculator installed. Shell expansions are evaluated recursively. %sh{echo '%{buffer_name}:%{cursor_line}'} for example executes a command like echo 'README.md:1': the variables within the %sh{..} expansion are evaluated before executing the shell command.
  • Register %reg{..}. The contents should be a single character representing the register name. For example, :set-register a hello world followed by echo %reg{a} prints hello world to the statusline.

As mentioned above, double quotes can be used to surround arguments containing spaces but also support expansions within the quoted content unlike single quotes or backticks. For example :echo "circle: %u{25CF}" prints circle: ● to the statusline while :echo 'circle: %u{25CF}' prints circle: %u{25CF}.

Note that expansions are only evaluated once the Enter key is pressed in command mode.

Exceptions

The following commands support expansions but otherwise pass the given argument directly to the shell program without interpreting quotes:

  • :insert-output
  • :append-output
  • :pipe
  • :pipe-to
  • :run-shell-command

For example executing :sh echo "%{buffer_name}:%{cursor_column}" would pass text like echo "README.md:1" as an argument to the shell program: the expansions are evaluated but not the quotes. As mentioned above, percent characters can be used in shell commands by doubling the percent character. To insert the output of a command like date -u +'%Y-%m-%d' use :insert-output date -u +'%%Y-%%m-%%d'.

The :set-option and :toggle-option commands use regular parsing for the first argument - the config option name - and parse the rest depending on the config option’s type. :set-option interprets the second argument as a string for string config options and parses everything else as JSON.

:toggle-option’s behavior depends on the JSON type of the config option supplied as the first argument:

  • Booleans: only the config option name should be provided. For example :toggle-option auto-format will flip the auto-format option.
  • Strings: the rest of the command line is parsed with regular quoting rules. For example :toggle-option indent-heuristic hybrid tree-sitter simple cycles through “hybrid”, “tree-sitter” and “simple” values on each invocation of the command.
  • Numbers, arrays and objects: the rest of the command line is parsed as a stream of JSON values. For example :toggle-option rulers [81] [51, 73] cycles through [81] and [51, 73].

When providing multiple values to :toggle-option there should be no duplicates. :toggle-option indent-heuristic hybrid simple tree-sitter simple for example would only toggle between “hybrid” and “tree-sitter” values.

:lsp-workspace-command works similarly to :toggle-option. The first argument (if present) is parsed according to normal rules. The rest of the line is parsed as JSON values. Unlike :toggle-option, string arguments for a command must be quoted. For example :lsp-workspace-command lsp.Command "foo" "bar".

Language servers

Neohelix enables experimental shared language servers by default on Unix. Compatible editors share a backend and live unsaved documents. Set editor.lsp.shared = false to opt out; see the guide for limits.

Helix has built-in support for the Language Server Protocol, providing IDE-like features — diagnostics, completion, goto-definition, rename and more, for any language that has a server configured. Language servers are separate programs you install yourself: the language support page lists which languages ship with a server configured, and the language server configuration wiki has per-server installation notes.

Run hx --health <language> to check whether Helix found the configured server for a language. After changing a server’s configuration, :lsp-restart reloads it and :lsp-stop stops it; :lsp-workspace-command runs a command the server exposes for the workspace.

Semantic highlighting and LSP extensions

Semantic highlighting

Neohelix overlays language-server semantic tokens on Tree-sitter highlighting. This lets the server distinguish resolved types, parameters, fields, methods, constants and other symbols that syntax alone cannot identify reliably. It is enabled by default with editor.lsp.semantic-tokens = true.

In Steel, use (lsp (hash 'semantic-tokens #t)), or change just that setting with (set-option! "lsp.semantic-tokens" #t). Toggle at runtime with :toggle lsp.semantic-tokens. To exclude one server, add "semantic-tokens" to its language entry’s except-features list.

  • Full-document requests are preferred; range-only servers are supported too. Delta responses and dynamic semantic-token registration are not negotiated yet.
  • Requests run outside rendering and edits are debounced by 100 ms. Responses from an old document version, request generation or server are discarded. Edits immediately discard old semantic positions; Tree-sitter supplies syntax colors while the new response is pending.
  • Server workspace/semanticTokens/refresh requests refresh affected documents. Compatible shared-LSP sessions route semantic-token requests normally.
  • Types map to existing theme scopes, including type, function.method, variable.parameter, variable.other.member and type.enum.variant. Rust-analyzer-specific token kinds include lifetimes, built-in types, Self, self, escapes and punctuation. Unknown types leave syntax colors untouched. readonly, defaultLibrary, mutable and documentation modifiers affect scope selection; not every server modifier has a separate visual treatment.
  • No LSP runs for finite diff rendering or picker previews: those remain Tree-sitter-highlighted. Semantic tokens do not add server startup to jjui.

Test with Rust source containing a struct, enum variants, fields, a trait method call and local variables. Wait for rust-analyzer initialization, then toggle semantic tokens; syntax colors must remain present in both modes. Edit while requests are pending, restart the server, and repeat with shared LSP enabled.

Protocol audit

Audited against this fork’s native client and rust-analyzer’s extension reference. LSP types existing in helix-lsp-types do not imply client/UI support.

Standard support already includes completion/snippets, diagnostics, hover, navigation, formatting/range formatting, rename and workspace edits, code actions, document links, inlay hints, document colors and call hierarchy.

Standard gaps include code lenses, type hierarchy, linked editing, on-type formatting, LSP folding ranges and selection ranges (Neohelix has Tree-sitter folding and syntax selection instead). Inlay-hint refresh is not advertised. Semantic-token delta and dynamic registration remain follow-ups.

There is no native rust-analyzer extension capability block or dedicated UI for the following groups:

Steel can send custom LSP requests/notifications and receive catch-all events, but that is a transport escape hatch, not implementation of these workflows. The shared-LSP broker isolates unknown extension operations into a private server; extension integrations need an audited sharing policy too.

Recommended order after semantic highlighting: macro expansion and navigation; runnables; actionable hover; snippet-aware refactors/SSR; test explorer and dependency navigation. Keep general protocol support in Rust and user-specific bindings/workflows in Steel.

Workspace trust

Helix has several features that can execute arbitrary code:

  • Language servers (LSP)
  • Debug adapters (DAP)
  • Local workspace configuration (.helix/config.toml, .helix/languages.toml)
  • Git integration (filters and other commands in a repository’s .git/config)

To protect against malicious projects (a checked-out PR, a freshly cloned repository, etc.) Helix gates these behind explicit per-workspace trust. By default language servers start automatically (their binaries come from $PATH, not from the workspace) and debug adapters may be launched, but loading .helix/config.toml or .helix/languages.toml and trusting a repository’s .git/config requires opting in. Note that debug adapters are never started automatically — you launch them yourself — but the same trust level still gates whether they may run. The model is intentionally similar to direnv: you run :workspace-trust once per workspace and Helix remembers across sessions.

Granting trust

When Helix opens a file inside a workspace it has never seen before, a modal trust prompt asks:

  • Trust — allow the workspace permanently.
  • Never — exclude the workspace; never prompt again.

<Esc> (or any other dismissal) caches “untrusted for this session” so the prompt doesn’t re-fire for every file you open in the workspace. The next time you start Helix in that workspace, it’ll prompt again.

A small [⚠] indicator appears in the bottom-right of the editor (next to the macro-recording [@]) whenever the workspace is in restricted mode and running :workspace-trust would change observable behavior — i.e. when there’s a local config to load or an LSP that would start.

You can also run :workspace-trust / :workspace-untrust / :workspace-exclude directly from the typed command prompt.

Revoking trust

Run :workspace-untrust to revoke a workspace’s trust grant. The next time you open a file in that workspace, you’re back to the untrusted hint.

Detecting changes after trust was granted

When you trust a workspace, Helix records a hash of every file under .helix/. If those files change afterwards (a malicious checkout, an inadvertent rebase, etc.) Helix detects the mismatch on the next open and reports the workspace as stale:

Workspace `.helix/` config changed since `:workspace-trust`. Local config
not loaded. Run `:workspace-trust` to re-allow.

In the stale state, language servers continue to run (they use the globally-configured binaries on $PATH, which are unchanged), but .helix/config.toml and .helix/languages.toml are not loaded. Run :workspace-trust again to re-pin the new hash.

Storage

Trust grants live in data_dir()/workspace_trust/, one small file per workspace. The filename is the SHA-256 of the workspace’s absolute path; the contents look like:

path = /home/user/proj1
hash = sha256:abc123...
excluded = false
  • Linux, macOS: ~/.local/share/helix/workspace_trust/
  • Windows: %AppData%\Roaming\helix\workspace_trust\

The one-file-per-workspace shape is safe under multiple concurrent Helix instances — different workspaces never write the same file.

Recommended setups

Default: trust servers, prompt before loading workspace config.

[editor.workspace-trust]
level = "servers"
prompt = true

Language servers start automatically in every workspace — their binaries come from $PATH and are not workspace-controlled — and debug adapters you launch are allowed to run. The modal only appears when opening a file in a workspace whose .helix/config.toml or .helix/languages.toml would unlock something. Trust everything else with one keystroke per workspace, deny with another.

Maximum security: never prompt, trust each workspace by hand.

[editor.workspace-trust]
level = "none"
prompt = false

Nothing trusts implicitly: language servers, debug adapters, local config, and git Trust::Full are all off until you run :workspace-trust. The popup never appears; the [⚠] indicator in the bottom-right is your only signal that the current workspace is restricted. Suited to users who would rather grant trust as a deliberate action than dismiss a dialog.

Warning

level = "insecure" is highly discouraged. It implicitly trusts every workspace you open, which defeats the protection entirely: a checked-out PR with a malicious .helix/config.toml would get its configuration loaded and any language server it defines launched, with no prompt and no indicator. Only set this if you accept full responsibility for what’s in every project directory you cd into.

Trusting workspaces by path (discouraged)

If you keep all your repositories under a predictable layout, you can trust them in bulk with glob patterns instead of granting each workspace individually:

[editor.workspace-trust]
trusted = [
  "~/src/github.com/me/*",
  "~/work/repos/*",
]

A workspace whose path matches a pattern is trusted for everything, just as if you had run :workspace-trust in it. ~ and environment variables are expanded.

Warning

This is weaker than an explicit grant and is discouraged. It skips the .helix/ change detection entirely (a malicious checkout under a matched directory is never flagged as stale), and it trusts any repository that later lands under a matching path — including one you clone into ~/src/github.com/me/ from an untrusted source. Prefer granting trust per workspace; reach for this only if the prompts are genuinely disruptive to your workflow. An explicit :workspace-exclude still overrides a matching pattern.

VCS trust

Git

Workspace trust also gates how Helix opens git repositories. Untrusted workspaces are opened in gix’s Trust::Reduced mode; trusted workspaces use Trust::Full.

Under Trust::Reduced, gix still runs the full filter pipeline (so built-in conversions like core.autocrlf keep working) but ignores configuration coming from the untrusted, repository-local .git/config. That means filter.*.clean / filter.*.smudge drivers and similar keys that would otherwise execute external programs are dropped until you trust the workspace.

Helix forces this trust level explicitly rather than letting gix infer it from .git directory ownership — a malicious .git/config in a directory you happen to own is still treated as untrusted until you run :workspace-trust.

Jujutsu

Jujutsu repositories are only supported when the workspace is fully trusted because Jujutsu itself does not expose a trust setting (yet).

Jujutsu itself is fairly secure in that it does not allow bringing a configuration on clone (JJ repository and workspace configuration live outside of their relevant directory) but there is no way to transmit the Trust::Reduced setting to underlying Git operations so we choose to not allow any JJ operation unless the workspace is fully trusted.

Note

If you use level = "servers", you will not get a prompt to enable full workspace trust by default, which means (for JJ repositories) that you will not get diff markers, branch name or a populated changed files picker until you run :workspace-trust manually.

Ecosystem

This section has information related to the wider Helix ecosystem.

Migrating from Vim

  • Delete/Change Commands
  • Navigation
  • Line Deletes
  • Comment lines, Completion, Search
  • File actions

Helix’s editing model is strongly inspired from Vim and Kakoune, and a notable difference from Vim (and the most striking similarity to Kakoune) is that Helix follows the selection → action model. This means that whatever you are going to act on (a word, a paragraph, a line, etc.) is selected first and the action itself (delete, change, yank, etc.) comes second. A cursor is simply a single width selection.

Note: As Helix is inspired by Vim and Kakoune, the keybindings are similar but also have some differences. The content of this page is inspired by Kakoune Wiki.

NOTE: Unlike vim, f, F, t and T are not confined to the current line.

Delete/Change Commands

delete a word:

  • vim: dw
  • helix: wd

change a word:

  • vim: cw
  • helix: ec or wc (includes the whitespace after the word)

delete a character:

  • vim: x
  • helix: d or ;d (; reduces the selection to a single char)

copy a line:

  • vim: yy
  • helix: Xy (X extends all selections to whole lines)

global replace:

  • vim: :%s/word/replacement/g<ret>
  • helix: %sword<ret>creplacement<esc>

Explanation: % selects the entire buffer, s opens a prompt for a regex, <ret> validates the regex and reduces the selection to each match (hence, all occurrences of word are selected). c deletes the selection contents and enter insert mode, replacement is typed and then <esc> goes back to normal mode.

Navigation

go to first line:

  • vim: gg
  • helix: gg

go to last line:

  • vim: G
  • helix: ge

go to line start:

  • vim: 0
  • helix: gh

go to line first non-blank character:

  • vim: ^
  • helix: gs

go to line end:

  • vim: $
  • helix: gl

jump to matching bracket:

  • vim: %
  • helix: mm

Line Deletes

delete to line end:

  • vim: D
  • helix: vgld or t<ret>d

Note: v is used along with gl (go to line end), because gl does not select text. t<ret> selects “’til” the newline represented by <ret>.

delete entire line:

  • vim: dd
  • helix: xd

Note: x selects the entire line under the cursor

Comment lines, Completion, Search

auto complete:

  • vim: C-p
  • helix: C-x

comment lines:

  • vim: gc
  • helix: Space-c

search for the word under the cursor:

  • vim: *
  • helix: A-o*n (if there’s a tree-sitter grammar or LSP) or be*n

Explanation: if there’s a grammar or LSP, A-o expands selection to the parent syntax node (which would be the word in our case). Then * uses the current selection as the search pattern, and n goes to the next occurrence. b selects to the beginning of the word, and e selects to the end of the word, effectively selecting the whole word.

block selection:

  • vim: C-v, then expand your selection vertically and horizontally
  • helix: There’s no “block selection” mode, so instead you’d use multiple cursors. Expand your block selection vertically by adding new cursors on the line below with C, and horizontally using standard movements

search “foo” and replace with “bar” in the current selection:

  • vim: :s/foo/bar/g<ret>
  • helix: sfoo<ret>cbar<esc>,

Explanation: s will open a prompt in the command line for a regex, and select all matches inside the selection (effectively adding a new cursor on each match). Pressing enter will then finalise this step, and allow the c to change the selections to “bar”. When done, go back to normal mode with <esc>, and keep only the primary selection with , (remove all the additional cursors).

File actions

select the whole file:

  • vim: ggVG
  • helix: %

reload a file from disk:

  • vim: :e<ret>
  • helix: :reload<ret> (or :reload-all<ret> to reload all the buffers)

run shell command:

  • vim: :!command
  • helix: :sh command (or !command to insert its output into the buffer)

setting a bookmark (bookmarking a location):

  • vim: ma to set bookmark with name a. Use `a to go back to this bookmarked location.
  • helix: there are no named bookmarks, but you can save a location in the jumplist with C-s, then jump back to that location by opening the jumplist picker with <space>-j, or back in the jumplist with C-o and forward with C-i

Helix allows some limited movement in insert mode without switching to normal mode.

Unlike Vim, under Helix, the cursor shape is the same (block) in insert mode and normal mode by default. This can be adjusted in configuration:

[editor.cursor-shape]
insert = "bar"

Helix’ keymap and interaction model (Using Helix) is easier to adopt if it can be used consistently in many editing contexts. Yet, certain use cases cannot easily be addressed directly in Helix. “Helix mode” is frequently still in early stages or missing entirely. For such cases, we also link to relevant bugs or discussions.

Neohelix supports both TOML and Steel configuration. The TOML example below is optional; a Steel-only setup does not need an empty config.toml. User configuration loads before trusted project configuration.

To override global configuration parameters, create a config.toml file located in your config directory:

  • Linux and Mac: ~/.config/helix/config.toml
  • Windows: %AppData%\helix\config.toml

💡 You can easily open the config file by typing :config-open within Helix normal mode.

Example config:

theme = "onedark"

[editor]
line-number = "relative"
mouse = false

[editor.cursor-shape]
insert = "bar"
normal = "block"
select = "underline"

[editor.file-picker]

You can use a custom configuration file by specifying it with the -c or --config command line argument, for example hx -c path/to/custom-config.toml. You can reload the config file by issuing the :config-reload command. Alternatively, on Unix operating systems, you can reload it by sending the USR1 signal to the Helix process, such as by using the command pkill -USR1 hx.

Finally, you can have a config.toml and a languages.toml local to a project by putting it under a .helix directory in your repository. Its settings will be merged with the configuration directory and the built-in configuration.

[editor.inline-blame] Section

Inline blame is virtual text that appears at the end of a line, displaying information about the most recent commit that affected this line.

KeyDescriptionDefault
showWhen to show inline blame"never"

show can be one of the following:

  • "all-lines": Inline blame is on every line.
  • "cursor-line": Inline blame is only on the line of the primary cursor.
  • "never": Do not render inline blame.

With automatic fetching disabled, inline blame needs an explicit request before it can appear. That plugin and the full-file :blame-toggle gutter are independent of inline blame display.

  • author: The author of the commit
  • date: When the commit was made
  • time-ago: How long ago the commit was made
  • title: The title of the commit
  • body: The body of the commit
  • commit: The short hex SHA1 hash of the commit
  • email: The email of the author of the commit

Themes

Themes

To use a theme add theme = "<name>" to the top of your config.toml file, or select it during runtime using :theme <name>.

Separate themes can be configured for light and dark modes. On terminals supporting mode 2031 dark/light detection, the theme mode is detected from the terminal.

[theme]
dark = "catppuccin_frappe"
light = "catppuccin_latte"
## Optional. Used if the terminal doesn't declare a preference.
## Defaults to the theme set for `dark` if not specified.
# fallback = "catppuccin_frappe"

Creating a theme

Create a file with the name of your theme as the file name (i.e mytheme.toml) and place it in your themes directory (i.e ~/.config/helix/themes or %AppData%\helix\themes on Windows). The directory might have to be created beforehand.

💡 The names “default” and “base16_default” are reserved for built-in themes and cannot be overridden by user-defined themes.

Overview

Each line in the theme file is specified as below:

key = { fg = "#ffffff", bg = "#000000", underline = { color = "#ff0000", style = "curl"}, modifiers = ["bold", "italic"] }

Where key represents what you want to style, fg specifies the foreground color, bg the background color, underline the underline style/color, and modifiers is a list of style modifiers. bg, underline and modifiers can be omitted to defer to the defaults.

To specify only the foreground color:

# Valid hex-color format is `#RGB` or `#RRGGBB`
# (each letter is a nibble)
key = "#ffffff"

If the key contains a dot '.', it must be quoted to prevent it being parsed as a dotted key.

"key.key" = "#fff"

Color values must be either a CSS hex RGB string or a name declared in the palette.

💡 Note that Helix doesn’t support transparency (alpha channel).

For inspiration, you can find the default theme.toml here and user-submitted themes here.

The details of theme creation

Color palettes

It’s recommended to define a palette of named colors, and refer to them in the configuration values in your theme. To do this, add a table called palette to your theme file:

"ui.background" = "white"
"ui.text" = "black"

Icons

Requirements

File-type and symbol-kind icons require a patched font such as NerdFonts to be installed and configured in your terminal emulator. These types of fonts are called patched fonts because they define arbitrary symbols for a range of Unicode values, which may vary from one font to another. Therefore, you need to use an icon flavor adapted to your configured terminal font, otherwise you may end up with undefined characters and mismatched icons.

To enable file-type and symbol-kind icons within the editor, see the [editor.icons] section of the configuration file.

To use an icon flavor add icons = "<name>" to your config.toml at the very top of the file before the first section or select it during runtime using :icons <name>.

Creating an icon flavor

Create a file with the name of your icon flavor as file name (i.e myicons.toml) and place it in your icons directory (i.e ~/.config/helix/icons). The directory might have to be created beforehand.

The name “default” is reserved for the builtin icons and cannot be overridden by user defined icons.

The name of the icon flavor must be set using the name key.

The default icons.toml can be found here, and user submitted icon flavors here.

Icons flavors have five sections:

  • Diagnostics
  • Breakpoints
  • Diff
  • Symbol kinds
  • Mime types

Each line in these sections is specified as below:

key = { icon = "…", color = "#ff0000" }

where key represents what you want to style, icon specifies the character to show as the icon, and color specifies the foreground color of the icon. color can be omitted to defer to the defaults.

Diagnostic icons

The [diagnostic] section defines four required diagnostic icons:

  • error
  • warning
  • info
  • hint

These icons appear in the gutter, in the diagnostic pickers as well as in the status line diagnostic component. By default, they have the foreground color defined in the current theme’s corresponding keys.

An icon flavor TOML file must define all of these icons.

Diff icons

The [diff] section defines three required diffing icons:

  • added
  • deleted
  • modified

These icons appear in the gutter. By default, they have the foreground color defined in the current theme’s corresponding keys.

An icon flavor TOML file must define all of these icons.

Breakpoint icons

The [breakpoint] section defines two required breakpoint icons:

  • verified
  • unverified

These icons appear in the gutter while using the Debug Adapter Protocol (DAP). Their color depends on the breakpoint’s condition and log message, it cannot be overridden by the color key.

An icon flavor TOML file must define all of these icons.

Symbol kinds icons

The [symbol-kind] section defines optional icons for the following required LSP-defined symbol kinds:

  • file (this icon is also used on files for which the mime type has not been defined in the next section, as a “generic file” icon)
  • module
  • namespace
  • package
  • class
  • method
  • property
  • field
  • constructor
  • enumeration
  • interface
  • variable
  • function
  • constant
  • string
  • number
  • boolean
  • array
  • object
  • key
  • null
  • enum-member
  • structure
  • event
  • operator
  • type-parameter

By default, these icons have the same style as the loaded theme’s keyword key. Their style can be customized using the symbolkind key in the theme configuration file, or it can individually be overridden by their color key.

An icon flavor TOML file must define either none or all of these icons.

Mime types icons

The [mime-type] section defines optional icons for mime types or filename, such as:

[mime-type]
".bashrc" = { icon = "…", color = "#…" }
"LICENSE" = { icon = "…", color = "#…" }
"rs" = { icon = "…", color = "#…" }

These icons appear in the file picker, in the statusline file-type-icon component, and in the bufferline (when enabled).

An icon flavor TOML file can define none, some or all of these icons.

Inheritance

Extend upon other icon flavors by setting the inherits property to an existing theme.

name = "custom_nerdfonts"

# Override the icon for generic files:
[symbol-kind]
file = {icon = "…"}

# Override the icon for Rust files
[mime-type]

Key remapping

Key remapping

Helix currently supports one-way key remapping through a simple TOML configuration file. (More powerful solutions such as rebinding via commands will be available in the future).

There are three kinds of commands that can be used in keymaps:

  • Static commands: commands like move_char_right which are usually bound to keys and used for movement and editing. A list of static commands is available in the Keymap documentation and in the source code in helix-term/src/commands.rs at the invocation of static_commands! macro.
  • Typable commands: commands that can be executed from command mode (:), for example :write!. See the Commands documentation for a list of available typeable commands or the TypableCommandList declaration in the source code at helix-term/src/commands/typed.rs.
  • Macros: sequences of keys that are executed in order. These keybindings start with @ and then list any number of keys to be executed. For example @miw can be used to select the surrounding word. For now, macro keybindings are not allowed in keybinding sequences due to limitations in the way that command sequences are executed. Modifier keys (e.g. Alt+o) can be used like "<A-o>", e.g. "@miw<A-o>"

To remap keys, create a config.toml file in your helix configuration directory (default ~/.config/helix on Linux systems) with a structure like this:

💡 To set a modifier + key as a keymap, type A-X = ... or C-X = ... for Alt + X or Ctrl + X. Combine with Shift using a dash, e.g. C-S-esc. Within macros, wrap them in <>, e.g. <A-X> and <C-X> to distinguish from the A or C keys.

# At most one section each of 'keys.normal', 'keys.insert' and 'keys.select'
[keys.normal]
C-s = ":w" # Maps Ctrl-s to the typable command :w which is an alias for :write (save file)
C-o = ":open ~/.config/helix/config.toml" # Maps Ctrl-o to opening of the helix config file
a = "move_char_left" # Maps the 'a' key to the move_char_left command
w = "move_line_up" # Maps the 'w' key move_line_up
"C-S-esc" = "extend_line" # Maps Ctrl-Shift-Escape to extend_line
g = { a = "code_action" } # Maps `ga` to show possible code actions
"ret" = ["open_below", "normal_mode"] # Maps the enter key to open_below then re-enter normal mode
"A-x" = "@x<A-d>" # Maps Alt-x to a macro selecting the whole line and deleting it without yanking it

[keys.insert]
"A-x" = "normal_mode"     # Maps Alt-X to enter normal mode
j = { k = "normal_mode" } # Maps `jk` to exit insert mode

Minor modes

Minor modes are accessed by pressing a key (usually from normal mode), giving access to dedicated bindings. Bindings can be modified or added by nesting definitions.

[keys.insert.j]
k = "normal_mode" # Maps `jk` to exit insert mode

[keys.normal.g]
a = "code_action" # Maps `ga` to show possible code actions

# invert `j` and `k` in view mode
[keys.normal.z]
j = "scroll_up"
k = "scroll_down"

# create a new minor mode bound to `+`
[keys.normal."+"]
m = ":run-shell-command make"
c = ":run-shell-command cargo build"
t = ":run-shell-command cargo test"

Ctrl, Shift and Alt modifiers are encoded respectively with the prefixes C-, S- and A-.

The Super key - the Windows/Linux key or the Command key on Mac keyboards - is also supported when using a terminal emulator that supports the enhanced keyboard protocol. The super key is encoded with prefixes Meta-, Cmd- or Win-. These are all synonyms for the super modifier - binding a key with a Win- modifier will mean it can be used with the Windows/Linux key or the Command key.

[keys.normal]
C-s = ":write" # Ctrl and 's' to write
Cmd-s = ":write" # Cmd or Win or Meta and 's' to write

Languages

Languages

Neohelix can also configure languages, servers and formatters through Steel. TOML remains supported; Steel-only setups do not need a languages.toml file.

Language-specific settings and settings for language servers are configured in languages.toml files.

languages.toml files

There are three possible locations for a languages.toml file:

  1. In the Helix source code, which lives in the Helix repository. It provides the default configurations for languages and language servers.

  2. In your configuration directory. This overrides values from the built-in language configuration. For example, to disable auto-formatting for Rust:

    # in <config_dir>/helix/languages.toml

[language-server.mylang-lsp]
command = "mylang-lsp"

[[language]]
name = "rust"
auto-format = false

  3. In a .helix folder in your project. Language configuration may also be overridden local to a project by creating a languages.toml file in a .helix folder. Its settings will be merged with the language configuration in the configuration directory and the built-in configuration.

Language configuration

Each language is configured by adding a [[language]] section to a languages.toml file. For example:

[[language]]
name = "mylang"
scope = "source.mylang"
injection-regex = "mylang"
file-types = ["mylang", "myl"]
comment-tokens = "#"
indent = { tab-width = 2, unit = "  " }
formatter = { command = "mylang-formatter" , args = ["--stdin"] }
language-servers = [ "mylang-lsp" ]

These configuration keys are available:

Project and LSP root selection

This is the model Helix uses:

  • The workspace root is found once by walking upward from the current working directory and picking the first directory that contains .git, .svn, .jj, or .helix. If none are found, the current working directory is the workspace root.
  • Root markers (roots) are used only for LSP root selection and are found by starting at the file, not the folder Helix was opened in.
  • We use the topmost directory that has a root marker (we stop the search at the workspace root).
  • In most cases, root markers are enough. In some repos there are multiple nested root markers and whether you want the inner or outer one is project specific. For these situations, use workspace-lsp-roots to stop the search early in a particular directory.
  • workspace-lsp-roots is meant to be set in the project-specific config: $PROJECT/.helix/config.toml.

Interaction with required-root-patterns (a language_server configuration key):

  • After the LSP root is selected, Helix checks for required-root-patterns in that directory. If none match, the server is not started.
  • This is validation, not root detection.

File-type detection and the file-types key

Helix determines which language configuration to use based on the file-types key from the above section. file-types is a list of strings or tables, for example:

file-types = ["toml", { glob = "Makefile" }, { glob = ".git/config" }, { glob = ".github/workflows/*.yaml" } ]

When determining a language configuration to use, Helix searches the file-types with the following priorities:

  1. Glob: values in glob tables are checked against the full path of the given file. Globs are standard Unix-style path globs (e.g. the kind you use in Shell) and can be used to match paths for a specific prefix, suffix, directory, etc. In the above example, the { glob = "Makefile" } config would match files with the name Makefile, the { glob = ".git/config" } config would match config files in .git directories, and the { glob = ".github/workflows/*.yaml" } config would match any yaml files in .github/workflow directories. Note that globs should always use the Unix path separator / even on Windows systems; the matcher will automatically take the machine-specific separators into account. If the glob isn’t an absolute path or doesn’t already start with a glob prefix, */ will automatically be added to ensure it matches for any subdirectory.
  2. Extension: if there are no glob matches, any file-types string that matches the file extension of a given file wins. In the example above, the "toml" config matches files like Cargo.toml or languages.toml.

Configuring the formatter command

Command line expansions are supported in the arguments of the formatter command. In particular, the %{buffer_name} variable can be passed as argument to the formatter:

formatter = { command = "mylang-formatter" , args = ["--stdin", "--stdin-filename", "%{buffer_name}"] }

Configuring code actions on save

The code-actions-on-save key lists LSP code actions to run (in order) when the buffer is saved. The available actions depend on available language servers, below are common examples and may need adjusting for your setup.

# Python with ruff
[[language]]
name = "python"
code-actions-on-save = ["source.organizeImports", "source.fixAll"]

# TS/JS with tsserver
[[language]]
name = "typescript"
code-actions-on-save = ["source.addMissingImports.ts"]

# TS/JS with eslint
[[language]]
name = "javascript"
code-actions-on-save = ["source.fixAll.eslint", "source.organizeImports"]

Configuring Language Servers for a language

The language-servers attribute in a language tells helix which language servers are used for this language.

They have to be defined in the [language-server] table as described in the previous section.

Different languages can use the same language server instance, e.g. typescript-language-server is used for javascript, jsx, tsx and typescript by default.

The definition order of language servers affects the order in the results list of code action menu.

In case multiple language servers are specified in the language-servers attribute of a language, it’s often useful to only enable/disable certain language-server features for these language servers.

As an example, efm-lsp-prettier of the previous example is used only with a formatting command prettier, so everything else should be handled by the typescript-language-server (which is configured by default). The language configuration for typescript could look like this:

[[language]]
name = "typescript"
language-servers = [ { name = "efm-lsp-prettier", only-features = [ "format" ] }, "typescript-language-server" ]

or equivalent:

[[language]]
name = "typescript"
language-servers = [ { name = "typescript-language-server", except-features = [ "format" ] }, "efm-lsp-prettier" ]

Each requested LSP feature is prioritized in the order of the language-servers array. For example, the first goto-definition supported language server (in this case typescript-language-server) will be taken for the relevant LSP request (command goto_definition). The features diagnostics, code-action, completion, document-symbols and workspace-symbols are an exception to that rule, as they are working for all language servers at the same time and are merged together, if enabled for the language. If no except-features or only-features is given, all features for the language server are enabled. If a language server itself doesn’t support a feature, the next language server array entry will be tried (and so on).

The list of supported features is:

  • format
  • goto-declaration
  • goto-definition
  • goto-type-definition
  • goto-reference
  • goto-implementation
  • signature-help
  • hover
  • document-highlight
  • completion
  • code-action
  • document-links
  • workspace-command
  • document-symbols
  • workspace-symbols
  • diagnostics
  • pull-diagnostics
  • rename-symbol
  • inlay-hints
  • document-colors
  • semantic-tokens

Tree-sitter grammar configuration

The source for a language’s tree-sitter grammar is specified in a [[grammar]] section in languages.toml. For example:

[[grammar]]
name = "mylang"
source = { git = "https://github.com/example/mylang", rev = "a250c4582510ff34767ec3b7dcdd3c24e8c8aa68" }

Grammar configuration takes these keys:

KeyDescription
nameThe name of the tree-sitter grammar
sourceThe method of fetching the grammar - a table with a schema defined below

Where source is a table with either these keys when using a grammar from a git repository:

KeyDescription
gitA git remote URL from which the grammar should be cloned
revThe revision (commit hash or tag) which should be fetched
subpathA path within the grammar directory which should be built. Some grammar repositories host multiple grammars (for example tree-sitter-typescript and tree-sitter-ocaml) in subdirectories. This key is used to point hx --grammar build to the correct path for compilation. When omitted, the root of repository is used

Choosing grammars

You may use a top-level use-grammars key to control which grammars are fetched and built when using hx --grammar fetch and hx --grammar build.

# Note: this key must come **before** the [[language]] and [[grammar]] sections
use-grammars = { only = [ "rust", "c", "cpp" ] }
# or
use-grammars = { except = [ "yaml", "json" ] }

When omitted, all grammars are fetched and built.

Guides

This section contains guides for adding new languages to Helix: language and grammar configuration, and the tree-sitter query files that drive highlighting, power indentation, textobjects, symbol tags, and other features.

Adding languages

Adding new languages to Helix

In order to add a new language to Helix, you will need to follow the steps below.

Language configuration

  1. Add a new [[language]] entry in the languages.toml file and provide the necessary configuration for the new language. For more information on language configuration, refer to the language configuration section of the documentation. A new language server can be added by extending the [language-server] table in the same file.
  2. If you are adding a new language or updating an existing language server configuration, run the command cargo xtask docgen to update the Language Support documentation.

💡 If you are adding a new Language Server configuration, make sure to update the Language Server Wiki with the installation instructions.

Grammar configuration

  1. If a tree-sitter grammar is available for the new language, add a new [[grammar]] entry to the languages.toml file.
  2. If you are testing the grammar locally, you can use the source.path key with an absolute path to the grammar. However, before submitting a pull request, make sure to switch to using source.git.

Queries

  1. In order to provide syntax highlighting and indentation for the new language, you will need to add queries.

Adding highlight queries

Adding highlight queries

highlights.scm queries assign a highlight scope (@function, @type, @keyword, …) to nodes in the syntax tree; the theme then maps each scope to a colour. Highlighting is the one query file that every language needs.

Query files should be placed in runtime/queries/{language}/highlights.scm when contributing to Helix.

Scopes

The full list of highlight scopes, and what each is for, is documented on the themes page. Match the most specific scope that fits the node — for example a method call is @function.method while a plain field access is @variable.other.member.

A query file may reuse another language’s with ; inherits: <lang> on the first line (for example tsx inherits typescript, which inherits ecma). An inherited file is compiled against each inheriting grammar, so every capture must be valid there too.

Precedence

Two rules decide which capture wins when more than one matches the same text:

  1. Same span: last match wins. Among captures covering the same bytes, the pattern that appears later in the file wins. Put a generic rule before the specific one that should override it.
  2. Nested nodes: innermost wins. When a parent and a child node both cover the text, the child’s capture wins, regardless of file order.

A common consequence of rule 2: capture the leaf you mean. A call captured on a wrapping node loses to a base (identifier) @variable on the inner identifier, so put @function on the identifier itself.

Where the grammar can’t distinguish a scope, casing is often used as a heuristic:

((identifier) @constant
 (#match? @constant "^[A-Z][A-Z_]*$"))

Testing

cargo xtask query-check [language] confirms the queries are valid against the grammar. cargo xtask highlight-check [language] runs the real highlighter over the fixtures in tests/query/highlights/<language-id>/<name>.<ext>, where a caret comment line (// ^ @capture) asserts the winning scope at the column above it; this catches the precedence mistakes that query-check cannot see. cargo xtask highlight-check --dump <language> <file> prints the winning capture per span for an arbitrary file.

Adding locals queries

Adding Locals Queries

locals.scm queries teach Helix about variable scopes and definitions so that local variables can be highlighted distinctly from global ones. When a @local.reference identifier is resolved to a @local.definition, it inherits the highlight class of that definition rather than the class assigned by highlights.scm.

Query files should be placed in runtime/queries/{language}/locals.scm when contributing to Helix. Like other query files, locals.scm may reuse another language’s with ; inherits: <lang> on the first line. Locals are resolved in their own pass with their own precedence, independently of highlights.scm.

Captures

@local.scope

Marks a node as a scope boundary. Definitions are only visible to references that appear inside the same scope or a nested one. Typical scope nodes are function bodies and blocks.

[
  (function_definition)
  (block)
] @local.scope

@local.definition.*

Marks a name node as introducing a local symbol. The suffix after @local.definition. becomes the highlight class applied to any reference that resolves to this definition. For example, @local.definition.variable.parameter causes matching references to be highlighted as variable.parameter.

(function_item
  (parameters
    (parameter
      pattern: (identifier) @local.definition.variable.parameter)))

Common suffixes mirror the highlight classes in highlights.scm: variable, variable.parameter, variable.builtin, variable.mutable, function, namespace, type, constant, etc.

@local.reference

Marks an identifier node as a potential reference to a local definition. Helix searches enclosing scopes for a matching definition and, if found, highlights the reference with that definition’s class instead.

(identifier) @local.reference

Discard captures

Any capture in locals.scm that is not @local.scope, @local.reference, or @local.definition.* acts as a discard. It prevents a @local.reference from being resolved at that node without affecting the highlights.scm result. This is useful for identifier nodes that look like references but should not be treated as variable references, for example keyword argument names or struct field names in struct literals.

; Keyword argument names in a call are not variable references.
(keyword_argument
  name: (identifier) @_)

Later patterns in a query file have higher precedence than earlier ones. A discard pattern must appear after the @local.reference pattern it is intended to override. Placing it later ensures it takes precedence and cancels the reference resolution for nodes it matches.

The convention is to use a capture name beginning with an underscore (e.g. @_, @_keyword) to make the discard intent clear, but any non-@local.* name works.

How definitions and references are matched

Helix matches references to definitions by comparing the text of the reference node against the text of definitions visible from the current scope. Definitions in inner scopes shadow those in outer scopes. If no definition is found the reference is left with its highlights.scm highlight.

Relationship with highlights.scm

The locals system runs alongside highlights.scm, not instead of it. highlights.scm always determines the baseline highlight for a node. locals.scm can override that highlight only when a @local.reference successfully resolves to a @local.definition, and only for that specific resolution. Non-@local.* captures in locals.scm (i.e. discards) have no effect on highlights.scm results.

Adding indent queries

Adding indent queries

Helix uses tree-sitter to correctly indent new lines. This requires a tree-sitter grammar and an indent.scm query file placed in runtime/queries/{language}/indents.scm.

The indent level of a line is the number of @indent scopes that contain it. An @indent capture on a node opens a scope spanning the lines after the node’s first line through its last line; a line is indented once for every such scope wrapping it. (A few capture types adjust this — @outdent cancels a level, @align aligns to a column, etc. (see Capture types.)

Note that it matters where these scopes begin: multiple scopes that open on the same physical line only increase the indent by 1 (the same-line rule). See Capture types.

By default, Helix uses the hybrid indentation heuristic. This means that indent queries are not used to compute the expected absolute indentation of a line but rather the expected difference in indentation between the new and an already existing line. This difference is then added to the actual indentation of the already existing line. Since this makes errors in the indent queries harder to find, it is recommended to disable it when testing via :set indent-heuristic tree-sitter. The rest of this guide assumes that the tree-sitter heuristic is used.

Indent queries

When Helix is inserting a new line through o, O, or <ret>, to determine the indent level for the new line, the query in indents.scm is run on the document. The starting position of the query is the end of the line above where a new line will be inserted.

For o, the inserted line is the line below the cursor, so that starting position of the query is the end of the current line.

#![allow(unused)]
fn main() {
fn need_hero(some_hero: Hero, life: Life) -> {
    matches!(some_hero, Hero { // ←─────────────────╮
        strong: true,//←╮  ↑  ↑                     │
        fast: true,  // │  │  ╰── query start       │
        sure: true,  // │  ╰───── cursor            ├─ traversal 
        soon: true,  // ╰──────── new line inserted │  start node
    }) &&            //                             │
//  ↑                                               │
//  ╰───────────────────────────────────────────────╯
    some_hero > life
}
}

For O, the newly inserted line is the current line, so the starting position of the query is the end of the line above the cursor.

#![allow(unused)]
fn main() {
fn need_hero(some_hero: Hero, life: Life) -> { // ←─╮
    matches!(some_hero, Hero { // ←╮          ↑     │
        strong: true,//    ↑   ╭───╯          │     │
        fast: true,  //    │   │ query start ─╯     │
        sure: true,  //    ╰───┼ cursor             ├─ traversal
        soon: true,  //        ╰ new line inserted  │  start node
    }) &&            //                             │
    some_hero > life //                             │
} // ←──────────────────────────────────────────────╯
}

From this starting node, the syntax tree is walked up to the root, collecting every @indent/@outdent/@align/… capture on an ancestor. Each @indent ancestor whose scope contains the line counts for one indent level (scopes opening on the same line collapse to one); the capture types describe the adjustments.

Capture types

  • @indent: Open an indent scope on this node — every line it contains is indented one more level. Scopes that open on the same line collapse: multiple @indent beginning on one line only add 1. A node captured by both @indent and @outdent contributes nothing (its level is cancelled) — used e.g. for a nested else if that should not stack a second level. By default the scope opens at the node’s own first line; see the header scope to open it at the parent (header) line instead.
  • @outdent: Decrease by 1 the indent of the line on which this (usually a closing token like }/)/], or a keyword like else) begins.
  • @indent.always: Like @indent but does not collapse — multiple on the same line each add a level. The net level contribution is @indent.always − @outdent.always.
  • @outdent.always: Like @outdent but stacks, the counterpart to @indent.always.
  • @align (default scope all): Align everything inside this node to some anchor. The anchor is given by the start of the node captured by @anchor in the same pattern. Every pattern with an @align should contain exactly one @anchor. Indent (and outdent) for nodes below (in terms of their starting line) the @align node is added to the indentation required for alignment.
  • @extend: Extend the range of this node to the end of the line and to lines that are indented more than the line that this node starts on. This is useful for languages like Python, where for the purpose of indentation some nodes (like functions or classes) should also contain indented lines that follow them.
  • @extend.prevent-once: Prevents the first extension of an ancestor of this node. For example, in Python a return expression always ends the block that it is in. Note that this only stops the extension of the next @extend capture. If multiple ancestors are captured, only the extension of the innermost one is prevented. All other ancestors are unaffected (regardless of whether the innermost ancestor would actually have been extended).
  • @opaque: Mark a literal body such as a string, heredoc, or block comment. Lines that begin inside the captured node keep their existing indentation instead of being reindented, so the contents of multi-line literals are left untouched.

@indent / @outdent

Consider this example:

#![allow(unused)]
fn main() {
fn shout(things: Vec<Thing>) {
    //                       ↑
    //                       ├───────────────────────╮ indent level
    //                    @indent                    ├┄┄┄┄┄┄┄┄┄┄┄┄┄┄
    //                                               │
    let it_all = |out| { things.filter(|thing| { //  │      1
    //                 ↑                       ↑     │
    //                 ├───────────────────────┼─────┼┄┄┄┄┄┄┄┄┄┄┄┄┄┄
    //              @indent                 @indent  │
    //                                               │      2
        thing.can_do_with(out) //                    │
    })}; //                                          ├┄┄┄┄┄┄┄┄┄┄┄┄┄┄
  //↑↑↑                                              │      1
} //╰┼┴──────────────────────────────────────────────┴┄┄┄┄┄┄┄┄┄┄┄┄┄┄
// 3x @outdent
}
((block) @indent)
["}" ")"] @outdent

Note how on the second line two blocks open on the same line: since both scopes begin on that line they collapse, for a net increase of 1. On the last line, the three block scopes all contain it, but it begins with three @outdent } tokens that cancel them, so the line lands back at the enclosing level.

Same-line collapse

The collapse above is a deliberate, load-bearing invariant:

A line is indented by one level per physical line on which a containing @indent scope opens, not one level per scope. Several @indent scopes that open on the same line together add a single level.

This is what makes method/builder chains flatten instead of staircasing. Grammars typically nest a chain so each .method() link is a call inside a member_expression inside the previous link, and several of those nodes begin on the receiver’s line:

#![allow(unused)]
fn main() {
let x = thing       // ← chain opens here
    .foo()          // each link aligned one level in,
    .bar()          // not progressively deeper
    .baz();
}
(call_expression) @indent

Even though many call_expression/member_expression scopes contain the .bar() line, they all open on the thing line, so they collapse to a single level and the continuation lines line up. Without the collapse, every link would add a level and the chain would stair-step to the right.

If you instead want each scope to count even when several open on one line (for example YAML’s “list item and map both start on the same line”) opt out with @indent.always (described below), which does not collapse.

@extend / @extend.prevent-once

For an example of where @extend can be useful, consider Python, which is whitespace-sensitive.

]
  (parenthesized_expression)
  (function_definition)
  (class_definition)
] @indent


class Hero:
    def __init__(self, strong, fast, sure, soon):#  ←─╮
        self.is_strong = strong #                     │
        self.is_fast = fast     # ╭─── query start    │
        self.is_sure = sure     # │ ╭─ cursor         │
        self.is_soon = soon     # │ │                 │
        #     ↑            ↑      │ │                 │
        #     │            ╰──────╯ │                 │
        #     ╰─────────────────────╯                 │
        #                                             ├─ traversal
    def need_hero(self, life):         #              │  start node
        return (                       #              │
            self.is_strong             #              │
            and self.is_fast           #              │
            and self.is_sure           #              │
            and self.is_soon           #              │
            and self > life            #              │
        ) # ←─────────────────────────────────────────╯

Without braces to catch the scope of the function, the smallest descendant of the cursor on a line feed ends up being the entire inside of the class. Because of this, it will miss the entire function node and its indent capture, leading to an indent level one too small.

To address this case, @extend tells helix to “extend” the captured node’s span to the line feed and every consecutive line that has a greater indent level than the line of the node.

(parenthesized_expression) @indent

]
  (function_definition)
  (class_definition)
] @indent @extend

        self.is_strong = strong #                     │
        self.is_fast = fast     # ╭─── query start    ├─ traversal
        self.is_sure = sure     # │ ╭─ cursor         │  start node
        self.is_soon = soon     # │ │ ←───────────────╯
        #     ↑            ↑      │ │                 
        #     │            ╰──────╯ │
        #     ╰─────────────────────╯
    def need_hero(self, life):
        return (
            self.is_strong
            and self.is_fast
            and self.is_sure
            and self.is_soon
            and self > life
        )

Furthermore, there are some cases where extending to everything with a greater indent level may not be desirable. Consider the need_hero function above. If our cursor is on the last line of the returned expression.

    def __init__(self, strong, fast, sure, soon):
        self.is_strong = strong
        self.is_fast = fast
        self.is_sure = sure
        self.is_soon = soon

    def need_hero(self, life):

            and self.is_fast
            and self.is_sure

    #←────────── where cursor should go on new line

In Python, the are a few tokens that will always end a scope, such as a return statement. Since the scope ends, so should the indent level. But because the function span is extended to every line with a greater indent level, a new line would just continue on the same level. And an @outdent would not help us here either, since it would cause everything in the parentheses to become outdented as well.

To help, we need to signal an end to the extension. We can do this with @extend.prevent-once.

(parenthesized_expression) @indent

]
  (function_definition)
  (class_definition)
] @indent @extend

(return_statement) @extend.prevent-once

Brace-less bodies

A brace-less single-statement body — if (cond) with its statement on the next line and no {} — is a body the indent must wrap, but the body node’s own first line is the line that needs the indent (there is no separate opening line). Capture the body and give it the header scope, which opens the scope at the header (the captured node’s parent) line instead of the body’s own line, so the body line is contained:

(if_statement
  consequence: (_) @indent
  (#not-kind-eq? @indent "compound_statement")
  (#set! "scope" "header"))
(while_statement
  body: (_) @indent
  (#not-kind-eq? @indent "compound_statement")
  (#set! "scope" "header"))

The query already names exactly the brace-less body (the consequence: / body: field, with #not-kind-eq? skipping the braced form the surrounding block indents), so the engine just opens that capture’s scope at its parent — it does not itself inspect node kinds or field names. This works for a multi-line brace-less body too (e.g. one returning a lambda). Give else and do / while their own pattern (on the alternative / body field) so the trailing else / while keyword line is not indented along with the body.

@indent.always / @outdent.always

As mentioned before, normally if there is more than one @indent or @outdent capture on the same line, they are combined.

Sometimes, there are cases when you may want to ensure that every indent capture is additive, regardless of how many occur on the same line. Consider this example in YAML.

  - foo: bar
# ↑ ↑
# │ ╰─────────────── start of map
# ╰───────────────── start of list element
    baz: quux # ←─── cursor
    # ←───────────── where the cursor should go on a new line
    garply: waldo
  - quux:
      bar: baz
    xyzzy: thud
    fred: plugh

In YAML, you often have lists of maps. In these cases, the syntax is such that the list element and the map both start on the same line. But we really do want to start an indentation for each of these so that subsequent keys in the map hang over the list and align properly. This is where @indent.always helps.

((block_sequence_item) @item @indent.always @extend
  (#not-one-line? @item))

((block_mapping_pair
    key: (_) @key
    value: (_) @val
    (#not-same-line? @key @val)
  ) @indent.always @extend
)

Predicates

In some cases, an S-expression cannot express exactly what pattern should be matched. For that, tree-sitter allows for predicates to appear anywhere within a pattern, similar to how #set! declarations work:

(some_kind
  (child_kind) @indent
  (#predicate? arg1 arg2 ...)
)

The number of arguments depends on the predicate that’s used. Each argument is either a capture (@name) or a string ("some string"). The following predicates are supported by tree-sitter:

  • #eq?/#not-eq?: The first argument (a capture) must/must not be equal to the second argument (a capture or a string).

  • #match?/#not-match?: The first argument (a capture) must/must not match the regex given in the second argument (a string).

  • #any-of?/#not-any-of?: The first argument (a capture) must/must not be one of the other arguments (strings).

Additionally, we support some custom predicates for indent queries:

  • #not-kind-eq?: The kind of the first argument (a capture) must not be equal to the second argument (a string).

  • #same-line?/#not-same-line?: The captures given by the 2 arguments must/must not start on the same line.

  • #one-line?/#not-one-line?: The captures given by the fist argument must/must span a total of one line.

The header scope

By default an @indent scope opens at the captured node’s own first line, so the lines inside it are indented and its first line is not. Sometimes the node you must capture is the line that needs indenting — a brace-less body such as the statement after if (cond) (see Brace-less bodies). For this, set scope to header:

(if_statement
  consequence: (_) @indent
  (#not-kind-eq? @indent "compound_statement")
  (#set! "scope" "header"))

header opens the scope at the captured node’s parent (the if_statement header) line instead of the node’s own line, so the body’s first line is contained and indented. The query selects exactly the body, so the engine just honours the annotation — it does not match on node kinds or field names itself.

(Older queries used tail / all scopes to control whether a node’s first line was included; under the containment model those are no longer needed and have been removed. header is the one scope the engine reads.)

Testing

cargo xtask indent-check [language] checks the queries against the fixtures in tests/indent/<language-id>.<ext> in both modes: re-indenting each line and simulating a newline typed after it, so a rule that is correct one way but wrong the other is caught.

Adding injection queries

Adding Injection Queries

Writing language injection queries allows one to highlight a specific node as a different language. In addition to the standard language injection options used by tree-sitter, there are a few Helix specific extensions that allow for more control.

Injection drives more than highlighting: within an injected region Helix also uses the injected language’s own indentation, textobjects, and comment tokens — so, for example, editing JavaScript inside an HTML <script> indents and comments as JavaScript.

An example of a simple query that would highlight all strings as bash in Nix:

((string_expression (string_fragment) @injection.content)
  (#set! injection.language "bash"))

Another example is this query, which highlights links in comments and keywords like “TODO”, by reusing the dedicated “comment” language:

((comment) @injection.content
  (#set! injection.language "comment"))

Capture Types

  • @injection.language (standard): The captured node may contain the language name used to highlight the node captured by @injection.content.

  • @injection.content (standard): Marks the content to be highlighted as the language captured with @injection.language et al.

  • @injection.filename (extension): The captured node may contain a filename with a file-extension known to Helix, highlighting @injection.content as that language. This uses the language extensions defined in both the default languages.toml distributed with Helix, as well as user defined languages.

  • @injection.shebang (extension): The captured node may contain a shebang used to choose a language to highlight as. This also uses the shebangs defined in the default and user languages.toml.

Settings

  • injection.combined (standard): Indicates that all the matching nodes in the tree should have their content parsed as one nested document.

  • injection.language (standard): Forces the captured content to be highlighted as the given language

  • injection.include-children (standard): Indicates that the content node’s entire text should be re-parsed, including the text of its child nodes. By default, child nodes’ text will be excluded from the injected document.

  • injection.include-unnamed-children (extension): Same as injection.include-children but only for unnamed child nodes.

Predicates

  • #eq? (standard): The first argument (a capture) must be equal to the second argument (a capture or a string).

  • #match? (standard): The first argument (a capture) must match the regex given in the second argument (a string).

  • #any-of? (standard): The first argument (a capture) must be one of the other arguments (strings).

Adding tags queries

Adding tags queries

See tree-sitter’s documentation on Code Navigation Systems for more background on tags queries.

Helix provides LSP-like features such as document and workspace symbol pickers out-of-the-box for languages with tags.scm queries based on syntax trees. To be analyzed a language must have a tree-sitter grammar and a tags.scm query file which pattern matches interesting nodes from syntax trees.

Query files should be placed in runtime/queries/{language}/tags.scm when contributing to Helix. You may place these under your local runtime directory (~/.config/helix/runtime in Linux for example) for the sake of testing.

Captures

@definition.*

Marks a node as a symbol definition. The following definition captures are recognized:

Capture name

definition.constant
definition.enum
definition.field
definition.function
definition.interface
definition.macro
definition.module

Adding Rainbow Bracket Queries

Helix uses rainbows.scm tree-sitter query files to provide rainbow bracket functionality.

Tree-sitter queries are documented in the tree-sitter online documentation. If you’re writing queries for the first time, be sure to check out the section on syntax highlighting queries and on query syntax.

Rainbow queries have two captures: @rainbow.scope and @rainbow.bracket. @rainbow.scope should capture any node that increases the nesting level while @rainbow.bracket should capture any bracket nodes. Put another way: @rainbow.scope switches to the next rainbow color for all nodes in the tree under it while @rainbow.bracket paints captured nodes with the current rainbow color.

For an example, let’s add rainbow queries for the tree-sitter query (TSQ) language itself. These queries will go into a runtime/queries/tsq/rainbows.scm file in the repository root.

First we’ll add the @rainbow.bracket captures. TSQ only has parentheses and square brackets:

["(" ")" "[" "]"] @rainbow.bracket

The ordering of the nodes within the alternation (square brackets) is not taken into consideration.

Angle brackets need care: < and > are usually comparison operators too, so capturing them globally would rainbow-colour every comparison. Capture them only within the generic node instead, which also marks that node as a scope:

(type_arguments ["<" ">"] @rainbow.bracket) @rainbow.scope

Note: Why are these nodes quoted? Most syntax highlights capture text surrounded by parentheses. These are named nodes and correspond to the names of rules in the grammar. Brackets are usually written in tree-sitter grammars as literal strings, for example:

{
  // ...
  arguments: $ => seq("(", repeat($.argument), ")"),
  // ...
}

Nodes written as literal strings in tree-sitter grammars may be captured in queries with those same literal strings.

Then we’ll add @rainbow.scope captures. The easiest way to do this is to view the grammar.js file in the tree-sitter grammar’s repository. For TSQ, that file is here. As we scroll down the grammar.js, we see that the (alternation), (L36) (group) (L57), (named_node) (L59), (predicate) (L87) and (wildcard_node) (L97) nodes all contain literal parentheses or square brackets in their definitions. These nodes are all direct parents of brackets and happen to also be the nodes we want to change to the next rainbow color, so we capture them as @rainbow.scope.

[
  (group)
  (named_node)
  (wildcard_node)
  (predicate)
  (alternation)
] @rainbow.scope

This strategy works as a rule of thumb for most programming and configuration languages. Markup languages can be trickier and may take additional experimentation to find the correct nodes to use for scopes and brackets.

The :tree-sitter-subtree command shows the syntax tree under the primary selection in S-expression format and can be a useful tool for determining how to write a query.

Properties

The rainbow.include-children property may be applied to @rainbow.scope captures. By default, all @rainbow.bracket captures must be direct descendant of a node captured with @rainbow.scope in a syntax tree in order to be highlighted. The rainbow.include-children property disables that check and allows @rainbow.bracket captures to be highlighted if they are direct or indirect descendants of some node captured with @rainbow.scope.

For example, this property is used in the HTML rainbow queries.

For a document like <a>link</a>, the syntax tree is:

(element                   ; <a>link</a>
  (start_tag               ; <a>
    (tag_name))            ; a
  (text)                   ; link
  (end_tag                 ; </a>
    (tag_name)))           ; a

If we want to highlight the <, > and </ nodes with rainbow colors, we capture them as @rainbow.bracket:

["<" ">" "</"] @rainbow.bracket

And we capture (element) as @rainbow.scope because (element) nodes nest within each other: they increment the nesting level and switch to the next color in the rainbow.

(element) @rainbow.scope

But this combination of @rainbow.scope and @rainbow.bracket will not highlight any nodes. <, > and </ are children of the (start_tag) and (end_tag) nodes. We can’t capture (start_tag) and (end_tag) as @rainbow.scope because they don’t nest other elements. We can fix this case by removing the requirement that <, > and </ are direct descendants of (element) using the rainbow.include-children property.

((element) @rainbow.scope
 (#set! rainbow.include-children))

With this property set, <, >, and </ will highlight with rainbow colors even though they aren’t direct descendents of the (element) node.

rainbow.include-children is not necessary for the vast majority of programming languages. It is only necessary when the node that increments the nesting level (changes rainbow color) is not the direct parent of the bracket node.
